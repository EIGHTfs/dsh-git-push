# 提交纪律（git-commit-discipline）

> 核心一句话：**有副作用的操作前先提交检查点；提交信息写清「改了什么 + 功能进度」；提交可自主，推送要授权。**

## 一、什么时候必须提交

| 场景 | 动手前必做 |
|------|------------|
| 批量文件操作（复制/删除/移动/重命名/覆盖 ≥3 个） | 先 `git add -A` + `git commit`（检查点，不推送）再操作 |
| 移动 / 删除文件目录 | 先问是否建本地 git 还原点；同意则先 commit 再执行（用户说不用则跳过，但删除仍走回收站） |
| 整理文件 / 目录 / 归档归类 / 清理散落文件 | **任务第一步**就是提交检查点（不等批量操作时才做） |
| skill 新增 / 修改 / 删除 / 重命名 | 当场提交到它所在仓库（通用 skill → 技能仓库；插件 skill → 插件项目），不等批量、不等收尾 |
| 测试通过想保存进度 | 随时可 commit 作检查点（防丢失、留回退锚点） |
| 正式推送前 | 撤销零散提交（`git reset --soft <基线>`）→ 重写规范 README + 整理提交记录 → 一次干净提交 |

非 git 目录：无法建还原点，如实告知，改用备份（`cp -r` 到备份目录）；删除一律走回收站（`.trash`，可恢复），禁止 `rm -rf` 永久删除。

为什么：批量/整理/删除是副作用放大区，一次可能动几十上百个文件，误判难手工恢复；检查点是唯一可靠还原点，也让「改了什么」的 diff 清晰。

## 二、提交信息怎么写

两部分：**本次变更** + **功能进度三态**。

```
<type>(<scope>): 本次变更摘要

功能进度：
- 开发中：<功能A>、<功能B>
- 已开发完：<功能C>、<功能D>
- 未开始：<功能E>、<功能F>（无则写「无」）
```

- type：feat / fix / docs / chore / skill 等；摘要写清**做了什么**，禁止「update」「改了点东西」这类空泛词
- 三态按**当前真实进度**写，不照抄上次；完成一个就从「开发中」移到「已开发完」
- 小改动同样带三态（可精简）；推送前重写提交时，三态同步刷新
- 效果：`git log` 一拉就是项目进度快照，接手的人不用翻 README

## 三、提交 vs 推送

| 动作 | 授权 |
|------|------|
| commit | 可自主执行（测试通过即可，作检查点） |
| push | **必须先获授权**（用户明确同意，或回复中出现「✅ 任务完成」收尾标记） |

推送前必做：README 与实现对齐（功能表、版本记录、设计/地址章节）、提交记录整理成「一个逻辑变更 = 一个提交」、文档不含对话引用与未脱敏内容。

## 四、坑

- 提交漏了 `git add -A` 或漏新文件 → 提交不完整，回退时丢文件
- 未授权就 push → 违反推送纪律（推送前还要做整理）
- 批量操作前忘了提交 → 出错只能靠回收站逐个恢复，没有整体回退点
- 非 git 目录硬要建还原点 → 如实说明改用备份，别假称已备份

## 五、配套 skill

- `git-project-startup`：开工先对齐远端、读提交历史
- `github-operations`：GitHub 通道与项目恢复
- `versioning-rule`：版本号语义（推送前同步版本号）
- `safe-delete-trash`：删除进回收站可恢复
- `bugfix-auto-authority`：commit 可自主、push 需同意
