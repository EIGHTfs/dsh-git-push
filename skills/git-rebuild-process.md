# 重新建库流程（git-rebuild-process）

> 2026-08-21 用户（EIGHTfs）确立。开发者文档留档：`ai-work-archive/开发者文档/重新建库流程-20260821.md`。

## 一、流程（7 步，按序执行）

1. **建库**：在数据文件夹新建 git 仓库（`/vol1/@appshare/DeepSeekHarness/数据/`，可建子目录如 `数据/重建仓库`）
2. **分析提交点**：按原始项目**每次提交**重新分析合理提交点（原始提交可能杂乱，重梳理出有意义的 commit 点）——**提交点判定细则见第五节**
3. **长期任务**：建立任务清单，分步骤按顺序还原到提交点
4. **还原+复制**：每步还原一个提交点的文件状态 → 复制进新建 git
5. **提交**：新建 git 走 dsh-git-push 提交流程——**只 commit 不推送**
6. **推送**：全部转移完成后才推送新位置的仓库
7. **归位**：仓库移到根目录（.dsh 同级）「项目」文件夹（`/vol1/@appshare/DeepSeekHarness/项目/`）

## 三、纪律

- git 纪律：**未同意不推送**；提交可自主作检查点（bugfix-auto-authority）
- 推送前可撤销整理 README/提交记录再正式提交推送（commit-checkpoint-before-push-reorg）
- 长期任务分步骤不跳序（multi-task-todo-queue）
- 还原 = 复制不动原始项目，全程可回退

## 四、合理提交点判定（2026-08-21 用户补充，权威）

> **核心**：提交点 = **推送过的主版本**（feat/功能里程碑）；**推送过后修复过 bug 的提交不能算合理提交点**，应并入其所属主版本。

### 判定细则

1. **主版本 = 合理提交点**：源仓库中带版本号的 **feat/功能** 提交（如 v1.2.0/v1.3.0/…/v1.13.0）= 提交点骨架
2. **修复不单独成点**：推送（发布）后针对该版本修 bug 的提交（fix/补丁版本，如 v1.4.1/v1.5.1/v1.7.1/v1.7.2）**不能算合理提交点**——并入其主版本提交点，不单独拆开
3. **并入方式**：提交点取「主版本线的最终状态」文件树（含修复内容）；package.json 版本修正为**主版本号**；commit message 注明并入的修复（如 `v1.4.0（含 v1.4.1 修复：不再 kill -9 runner）`）
4. **docs/清理/跨项目杂项提交**：按时间就近并入相邻主版本提交点（内容随文件树自然包含），不单独成点
5. **版本号规范**：提交点版本号遵循 versioning-rule（1 开头、X.Y.Z、版本只在提交时变化）；源仓库漏 bump 的按规范修正（如 1.13.1 修复并入 1.13.0 时版本号归 1.13.0）
6. **初始提交**：无代码文档版 = 1.0.0（原理/架构/规划文档，最新规范定义）
