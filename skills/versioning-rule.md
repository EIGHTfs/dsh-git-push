# 版本号规则（versioning-rule）

> **权威源 = dsh-git-push 插件项目 skills/**（版本控制 skill 归 dsh-git-push 插件权威，2026-08-21 确立）；公用目录 .dsh/skills 与 ai-work-archive 为副本。（X.Y.Z 语义 + 版本只在提交时变化 + 1 开头硬规则 + 大版本换代判定）

> 适用范围（2026-08-18 扩展）：**本机所有 DSH 自研插件（dsh-*）** + gamebanana-mods-downloader 三组件（浏览器扩展/Server/画廊）。
> ⚠️ **硬规则（2026-08-18 约定，所有 AI 所有会话）**：**版本号大版本 X 必须 ≥ 1——禁止 0.x 版本号**（0.x 是不合规范的预发布写法，一经发现必须修正为 1.x）。

## 零、⭐ 核心规则：版本号只在提交时变化（2026-08-21 确立，最高优先）

> **原话**：「版本控制只在提交时变化，比如 2.0.0 哪怕开发 10 几个功能，也只是提交一次，保存 2.1.0」

- **版本号只在提交（commit）时变化**：开发过程中无论做了多少功能、改了多少代码，版本号一律不动
- **一次提交 = 一个小版本**：提交一次保存时，版本号升一个小版本（**2.0.0 → 2.1.0**）
- **功能个数不决定版本号**：哪怕开发 10 几个功能，只要只提交一次，版本号也只升一个小版本（2.1.0），**绝不按功能数逐个升**
- 一句话：**版本号指向「提交存档」而非「功能进度」**——Y = 第几次提交存档，不是第几个功能

### 落地细则

1. **开发期（未提交）**：`package.json` 等版本字段保持当前值不变，不随功能开发逐个改动
2. **提交时**：先把版本号 Y+1（Z 归 0），再提交；提交信息里的版本号与 package.json 一致
3. **一次提交内含的功能数不限**：版本号只反映提交存档次序，不反映功能数量
4. **bug 补丁提交**：同一提交版本存档后，修 bug 的补丁提交 → Y 不变、Z+1（仍只在提交时变化）
5. **大版本换代**（结构不同 X+1，见第三节）仍按提交时变化执行——一次提交内可同时完成 X+1
6. 内置模块（0.x 阶段，见第二节例外）同样遵守：模块版本只在提交时变化（0.1.0 → 0.2.0 也是一次提交）

### 正反例

- ✅ 2.0.0 开发了 10 几个功能，只提交一次 → 存档为 **2.1.0**（不管功能数）
- ❌ 2.0.0 每开发一个功能就升一次版本（2.0.0 → 2.1.0 → 2.2.0 → 2.3.0…）——**禁止**，版本不按功能数升
- ✅ 2.1.0 提交后修了 3 次 bug，3 次补丁提交 → 2.1.3
- ✅ 项目重构为新结构，一次提交 → 大版本 +1（如 2.1.0 → 3.0.0）

## 一、规则（X.Y.Z 语义）

- 格式：**X.Y.Z**（三个小数段）
  - **X** = 大版本（重大重构/不兼容变更才 +1；**X 从 1 起，禁止 0**）
  - **Y** = 提交版本序号（**每次提交 +1**；一次提交可含任意多个功能）
  - **Z** = 该提交版本的 **bug 修复次数**（同一提交版本存档后，修 bug 的补丁提交 +1）
- 版本号指向**当前最新提交的存档进度**（不是功能数/全局累计）
- **1.0.0（Y=0）默认含义**：**不含代码**的架构设计文档 + 任务清单 + README 文档（项目初始交付物，还没有任何功能代码；第一个功能提交落地才升到 1.1.0）

## 二、⭐ 硬规则：1 开头（禁止 0.x）

- **任何 DSH 自研插件 / 项目 package.json 的 `version` 字段必须 1 开头**（`1.x.x`），禁止 `0.x.x`
- 新建插件项目时 version 直接写 `1.0.0`（不要从 0.1.0 起）
- 已存在的 0.x：立即修正为 1.x（Y/Z 原样保留：0.2.0 → 1.2.0，0.10.0 → 1.10.0）
- 例外：**官方 `@deepseek-ai/*`、`@dsh-external/*` 第三方依赖的版本号由上游决定，不改**（检修时跳过）

### 反面教材（2026-08-18 实测）

dsh-session-manager 历史版本从 `0.1.0` 一路升到 `0.10.0`（0.x 序列），不合规范；
检修时一次性修正 **12 处** 0.x → 1.x（workspace 8 个插件 + 主实例/测试实例部署副本），
全部 Y/Z 保持（如 dsh-session-manager 0.10.0 → **1.10.0**）。教训：**建项目第一版就该 1 开头，别用 0.x 起步**。

### ⭐ 例外（2026-08-19 补充）：内置模块版本从 0 开始

- **内置模块** = 独立开发、最终 **burn-in 内置进正式插件**的小模块（如 dsh-workflow-audit → 并入 dsh-session-manager；开发模式见 dsh-link-bridge skill）
- 这类模块**独立阶段版本从 0 开始**：`v0.1.0` 起步（0.x = 待内置、未并入主插件）
- **内置成功后**：模块不再有独立版本，随主插件版本走（主插件 1.x）
- 适用示例：**dsh-workflow-audit v0.1.0**（2026-08-19 起）
- 与上面硬规则的关系：**正式插件（独立发布）必须 1 开头**；**内置模块（待内置）允许 0.x 起步**——两场景并存
- **版本只在提交时变化同样适用**：模块开发期版本不动，提交时 0.1.0 → 0.2.0（见第零节）

### 1.0.0 vs 0.1.0 的对应关系（2026-08-19 补充，⚠️ 必读）

- **插件主版本 `1.0.0`** = 无代码文档版：架构设计 + **模块设计思路** + 任务清单 + README（还没有任何功能代码）
- **功能模块实际写出来**（开始有代码）→ 该模块版本 = **`0.1.0`**（第一个功能，待内置）
- **每个功能模块都从 `0.1.0` 开始**（不是按模块序号排：第二个模块也是 0.1.0 起步）
- **模块内部有新功能/完善 → 提交时升 0.2**：0.1.0 → 0.2.0 → 0.3.0...（Y = 该模块的第几次提交存档，Z = bug 修复次数；版本只在提交时变化）
- 全部内置完成后：插件升 1.1.0（首个功能落地），后续模块内置随插件版本走

## 三、⭐ 大版本换代判定（2026-08-20 确立，自更新/版本比对必读）

> **结构不同 = 大版本换代（大版本 + 1）**。这条规则用于「判断远端版本是否真的是可自动更新的新版本」。

### 核心规则

1. **结构不同（structureMismatch）＝ 本地已处于新大版本结构（旧系列大版本 + 1）**
2. 旧结构的版本号（即使数字更高，如 1.13.0）属于**旧大版本系列**，**永远不构成"可自动更新的新版本"**
3. 新旧结构切换必须**人工处理**或等待新版本（同结构）正式提交——**禁止自动用旧结构覆盖新代码**

### 判定示例（dsh-git-rescue 实测，2026-08-20）

| 本地 | 远端 | 远端结构 | 判定 | 处理 |
|------|------|----------|------|------|
| 2.0.0（新根级结构） | 1.13.0（旧 components/ 子树） | 旧 | updateAvailable=true（版本号更高是事实）但 majorUpgrade=true | **不自动更新**，人工/等新版本提交 |
| 2.0.0 | 2.0.0（根级） | 同 | updateAvailable=false | 已是最新 |
| 2.0.0 | 2.1.0（根级） | 同 | updateAvailable=true + majorUpgrade=false | 可自动更新 |

### 落地（dsh-git-rescue 自更新）

- `lib/self-update.js` 的 `checkForUpdate()`：
  - 版本来源探测：根级 `package.json` 优先，旧位置 `components/git-rescue/package.json` 回退（**如实报告远端版本号**）
  - 结构校验：远端根必须存在 `lib/index.js`（新大版本结构）→ `structureMismatch` + `majorUpgrade`
  - 返回 `{ updateAvailable, structureMismatch, majorUpgrade, detail }`
- `applyUpdate()`：遇 `structureMismatch`/`majorUpgrade` **拒绝执行**（防旧结构覆盖新代码）
- 单测：T9/T9.5/T9.6（compareVersions / allowlist 路径 / 真实远端结构判定）

### 操作指引（遇到版本比对/自更新判断时）

1. 读远端 `package.json` 版本号（根级优先，旧位置回退）——**如实报告**
2. 检查远端结构是否与本地一致（根级 `lib/` 是否存在）——**结构不同 = 大版本换代**
3. 结构相同才允许自动更新；结构不同 → 人工处理 / 等新版本提交

## 六、落地位置

- **DSH 插件**：`package.json` 的 `version` 字段（唯一权威位置；插件加载信息、client bundle rev 均以它为准）
- gbmd 扩展：`extension/manifest.json` 的 `version`（MV3 要求 X.Y.Z 三段）
- gbmd Server：`server/package.json` + `server/app.js` 启动日志（`gbmd-server vX.Y.Z 已启动`）
- gbmd 画廊：`gallery/server.js` 头部注释（`gbmd-gallery vX.Y.Z`）
- README：更新日志标题（新功能提交必须整理 README 版本记录，见 release-docs-rule）
- CRX 打包名：`gamebanana-mods-downloader-vX.Y.Z.crx`

## 七、更新步骤（每次发版 / 改版本）

1. **确认当前版本号**（开发期版本号一律不动，见第零节）
2. **有功能/变更待提交** → 版本号升一个小版本：Y+1、Z 归 0（提交一次一个小版本，不按功能数升）
3. **数清该提交版本修了几次 bug Z**（bug 补丁提交 Y 不变、Z+1）
4. **检查当前版本是否 1 开头**——0.x 一律先修正再继续
5. **判断是否大版本换代**（结构是否变化）——结构变了则 X+1（见第三节）
6. 改对应文件的 version 字段（DSH 插件=package.json；gbmd=各自位置）
7. 同步 README 更新日志标题（release-docs-rule：新功能必须整理 README）
8. 部署副本同步（主实例 `~/.dsh/profiles/web/node_modules/<插件>/package.json`、测试实例 `node_modules_local`）
9. 提交（**提交即存档新版本号**；推送另按提交推送纪律）

## 八、检修清单（发现/怀疑版本号问题时）

- [ ] 扫 `package.json` version 是否 0.x（`grep '"version"' */package.json | grep '"0\.'`）
- [ ] 0.x → 1.x（Y/Z 保持），同步主实例/测试实例部署副本
- [ ] 第三方依赖（@deepseek-ai/@dsh-external）跳过
- [ ] 有 git 的项目各自提交（`chore: 版本号规范修正（大版本 1 开头）`）
- [ ] 结构是否变化（自更新是否会被旧结构版本误导）——结构不同 = 大版本换代
- [ ] **版本号是否只在提交时变化**——开发期乱升版本号（按功能数逐个升）要修正为提交时一次性升

## 九、注意

- **版本只在提交时变化（2026-08-21 确立）**：开发多少功能都不升版本，提交一次升一个小版本（2.0.0 → 2.1.0）；功能个数不决定版本号
- 功能"加→改→移除→恢复"算 **1 个功能**；移除+恢复合计算 1 次改动（功能计数只在整理 README 时用，不决定版本号）
- 合并类提交（如"gameIdFixes 合并"）算独立功能还是子步骤，按功能主题判断（只影响 README 描述，不影响版本号规则）
- 无法确定时，读 git log 按提交主题归类，或问用户
- 看到 **1.0.0** 一律按「无代码文档版」处理（架构设计+任务清单+README），不要误以为有功能；有代码的第一个功能提交落地从 1.1.0 起
- **看到旧结构高版本号（如 1.13.0）不要误判为可自动更新的新版本**——结构不同 = 大版本换代（第三节）
