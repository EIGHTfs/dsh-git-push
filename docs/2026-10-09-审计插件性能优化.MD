## 一、修改目标

- **问题描述**：插件（尤其**审计**链路）响应慢，体感"卡/要等"。
- **实测基线**（本方案编写时采集：静态 + 只读实测）：
  ```
  规模：lib/*.js = 149 文件 / 25079 行｜审计规则 21 条｜注册工具 16 个
  单次 git 子进程 = ~8ms（实测 5 次 rev-parse 共 39ms）
  由代码位置推算（静态，未跑全量审计）：
    lib/audit/orchestrate.js:431  逐文件 `git check-ignore`         ⇒ 8ms × 候选文件数（本仓 ~300 ⇒ ≈2.4s）
    lib/audit/collector.js:386    逐文件 `git ls-files --others --`  ⇒ 8ms × 候选文件数（同量级）
    lib/git/repos.js:121-136      每仓 5~6 次 spawn                 ⇒ 8ms × 6 × 仓库数（22 仓 ≈ 1.1s）
  ```
- **期望效果**（可衡量）：
  1. 审计同一仓库墙钟时间 **−30% 以上**；
  2. 审计链路的 **「每文件一次 git 子进程」降为 0**；
  3. `git_scan` 的 git 子进程数 **−50% 以上**；
  4. 插件**冷启动（模块加载）时间不增**。

## 二、潜在问题分析

| 风险类型 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 行为漂移（批量化后判定不同） | 高 | 漏检/误报 | 批量与逐文件语义逐条对齐；对照测试；结果哈希比对 |
| 缓存/记忆化用旧结果 | 中 | 审计失真 | 指纹含 mtime+size+schema 版本；先证冷热一致再启用 |
| 兼容性破坏 | 低 | 宿主/前端读不到字段 | 不改返回结构，只改内部实现 |
| 并发竞态 | 中 | 结果错乱 | 仅只读并发；写入与状态变更串行 |
| 小仓库反向变慢 | 中 | 体验变差 | 批量化设小规模阈值回退；小/中/大三档复测 |
| 依赖引入 | 低 | 违背零依赖 | 不新增任何 npm 依赖 |

**边界条件检查**：
1. 空仓库 / 0 候选文件 ⇒ 批量命令不得抛错，返回空集；
2. `git` 不可用或超时 ⇒ 退回逐文件路径并显式标注"未确认"；
3. 路径含空格/中文/换行 ⇒ 批量输入一律 `-z` / `--stdin`；
4. 扫描中途文件被改 ⇒ 指纹复核失败则重算该文件；
5. 符号链接 / 跨平台分隔符 ⇒ 沿用现有 realpath 与平台分支。

## 五、逐文件改动详情

### 5.1 lib/audit/orchestrate.js（L431 附近）
- 当前：每候选文件一次 `execFileSync('git', ['-C', repo, …'check-ignore','-q','--no-index','--', rel])`。
- 改为：一次 `git -C <repo> check-ignore --stdin -z --no-index` 批量喂入候选路径，取回被忽略集合；失败则降级逐文件并标注。
- 原因：子进程 8ms × 文件数线性放大。
- 影响：忽略判定是审计入参 ⇒ 必须与逐文件逐一对照。
- 原实现以注释保留（便于回退与对照）。

### 5.2 lib/audit/collector.js（L428 / L370 / L386）
- L428 逐文件 statSync ⇒ 复用 `readdirSync({withFileTypes})` 已得信息；
- L370 `git status --porcelain` + L386 逐文件 `git ls-files --others -- <rel>` ⇒ 仓库级一次全量未跟踪列表（`-z`），内存比对。

### 5.3 lib/git/repos.js（L121–136）
- 每仓 5~6 次 runGit ⇒ 合并取法 + 多仓只读并发（小并发、可配置）；返回字段形状完全不变。

### 5.4 lib/git/exec.js（可选，Step 6）
- 只读并发池（默认小并发，参数/配置可调）；写命令一律串行。

### 5.5 lib/ast/tokenizer.js（可选，Step 1）
- 缓存上限从"512 条"改为"按字节预算"（大小可配置），大文件仓库命中率提升。
