# 功能：审计引擎

> 面向使用者：讲清审计引擎「怎么组织、怎么判定、怎么评分、怎么扩展、结果怎么读」。
> 本文只覆盖审计侧；提交推送、npm 发布等 git 侧能力见《功能-发布与工具链》。

## 一句话

审计引擎是一套**规则声明与判定实现分离**的静态检查系统：规则写在 yml 里只声明「查什么」，判定逻辑在 `lib/ast/` 与 `lib/checks/`，编排调度在 `lib/audit/`，评分在 `lib/score/`。对外提供全量 / 变动集 / 历史提交三种范围，结果分级、可评分、可豁免。

## 一、三层结构

```
① 规则声明   lib/audit-rules/audit-rules-<槽位>.yml   只声明「查什么」，不含判定逻辑
② 判定实现   lib/ast/*                                 返回「应报的行号/命中集合」
③ 检查器包装 lib/checks/*                             把判定转成 finding（message/维度/豁免提示）
④ 编排调度   lib/audit/*                              收集文件 → 按 kind 调度 → 汇总 → 评分
⑤ 评分       lib/score/*                              10 维度加权得 0-100 + 等级
```

**槽位按语言与领域划分**：放一个 `audit-rules-<名>.yml` 即自动成为槽位（UI 规则包列表动态发现）。语言槽位（`python` / `cpp` / `go` / `java` / `php` / `rust` / `swift` / `nodejs` / `frontend` / `csharp`）只对对应扩展名生效；领域槽位（`security` / `paths` / `comment` / `docs` / `dsh` / `npm` / `performance` / `robustness` / `structure` / `filehealth` / `folder` / `private` / `i18n` / `template`）按主题组织。规则用 `exts` / `include_paths` / `exclude_paths` / `file_patterns` 限定作用域——`file_patterns` 是**内容**初筛而非路径，这是最容易写错的字段。

## 二、判定实现：语法树优先，token 级回退

同一精筛在语法树可用时走树语义，拿不到树时回退 token 级——**回退是常态路径，审计绝不因缺语法而失效**。编排层按 `TREE_FIRST_KINDS` 清单决定是否预解析建树；结果里有 `treeUsage`（建树数 / 回退数 / 无语法数 / 解析失败数 / 覆盖率）可观测。

已树化的两类判定：

| 精筛 | 树给的判据 | token 级的失灵 |
|---|---|---|
| `credential-value` | 赋值节点的左值/右值结构；bytes/raw 前缀是一等字符串节点 | 参数默认值、拼接右值、三元表达式全被误判成硬编码；`SECRET=b"…"` 整行漏报 |
| `short-func-name` | `method_definition` 等定义节点带 name 字段；`get`/`set` 访问器显式排除 | 只认 `function` 关键字，类方法/对象方法短名完全查不到 |

**新增树化判定的门槛**：① 双向样本测试跑出红基线 → ② 树化 → ③ 修绿 → ④ 无树对照（证明干净结果来自树而非规则变哑）→ ⑤ 登记 `TREE_FIRST_KINDS` → ⑥ 初筛 pattern 必须能命中新覆盖形态。

检查器的语言化沿同一模式：入口检测语言特征后分流，**语言无关核心 + 语言分支**，JS 路径不动、双语言回归。Python 用缩进块识别函数范围（`def name(...):` 起，缩进回退止），`func-lines` / `complexity` / `nesting` / `min-length` 各自有分支；C/Java/Go 等大括号语言可直接复用现有检查器。

## 三、分级、评分与覆盖度

- **分级**：`blocker`（拦截提交）/ `warning` / `notice`。提交门禁只数 blocker；示例目录内的 blocker 是规则演示，不拦真实提交。
- **评分**：10 维度加权（可读性 / 可维护性 / 健壮性 / 安全性 / 性能 / 测试覆盖 / 可观测性 / 可部署性 / 文档 / 开发者体验），`维度得分 = max(0.1, 10 − k × ln(1 + 命中次数))`，实际权重按命中文件数占该维度可作用文件数的比例缩放。
- **零规则维度记 0**：某维度若一条规则都没加载（`dimRuleCounts` 为 0），其权重归零并在结果里列出 `uncoveredDimensions`——不给「没有检测能力」发满分。
- **文档维度是加分制**：`docs-score` 检查器按 4 个结构信号（README 存在 / 版本号与 package.json 一致 / 有安装启动命令 / 有环境变量清单）给 0~10 分，只判「做了」不判「写得好」；加分项**不进 findings**，因此不污染问题数与门禁。版本不一致等判断不了的情况列「人工复核」提示，不自动扣分。

## 四、外部 linter 委托层

审计可以委托被审项目自带的官方 linter（当前支持 ruff），代码在 `lib/lint-adapter/`：`detect.js` 按配置指纹（`pyproject.toml` 的 `[tool.ruff]` 或 `ruff.toml`）判定是否启用并探测可执行文件，`runner.js` 调 `ruff check --output-format json --no-fix .` 并适配成统一 finding，`index.js` 聚合。

两条硬约束：

1. **只进评分与报告，绝不进拦截门禁**——外部 finding 的 severity 恒封顶 `warning`，别人的规则集不裁决本仓库能否提交。
2. **任何失败一律降级为空**（可执行缺失 / 超时 / 输出非 JSON / 退出码 ≥2，都返回 `{findings: [], note: 降级原因}`）；ruff 的退出码 `1` 表示有 lint 问题且 stdout 是合法 JSON，必须采纳。

探测顺序：环境变量 `DSH_GIT_PUSH_RUFF` → 插件 `tools/`（或 `tool/`）副本 → 被审项目 `tools/` → PATH 各段 → 常见位置；每条候选校验**可执行**而非仅存在（CIFS/noexec 上会存在但跑不动）。`linted` 数组随结果返回，把「委托成功有产出 / 委托成功无问题 / 有配置但工具不可用 / 项目没配 linter」四种情形分开记，工具不可用不再静默为空。ruff 副本放 `<插件根>/tools/ruff`；`package.json` 的 `files` 白名单不含 `tools/`，故副本随 git 入库但不进 npm 包，部署侧需另行放置。

## 五、审计范围

| 范围 | 入口 | 用途 |
|---|---|---|
| `full` | `code_audit scope=full` / `git-sluice audit --full` | 全仓体检；外部 linter 只在此范围委托 |
| `diff` | 默认 / `auditChanged` | 提交门禁，只看变动文件 |
| `history` | `code_audit history=true` / `git-sluice audit --history` | 逐提交快照回放，报告落盘；只出报告不拦提交 |

三种入口（插件工具 / CLI / HTTP `/api/git-push/audit`）共用同一套规则与评分。`groupBy=rule|file|severity|slot` 可聚合结果。

**判定是否为误报**有一套固定口径：误报＝规则**判错事实**（说存在其实不存在、说违规其实合规）；规则正确命中了真实存在的东西，哪怕本轮不想改，也是真命中。真命中不得用豁免标记掩盖，只能改代码或保留 blocker 上报。豁免（`dsh-skip-*` 标记 / `.auditignore`）的唯一用途是消除误报。

## 六、豁免通道

四条通道各司其职：

| 通道 | 位置 | 行为 |
|---|---|---|
| `.auditignore` 整文件 | 路径行 | 该文件全部规则不审，采集期就不收 |
| `.auditignore` 细粒度 | `路径 : slot/rule # 理由` | 只免指定规则，报告单列「已确认豁免 N 条」 |
| `dsh-skip-*` 标记 | 文件头前 3 行 / 行尾 | 按标记覆盖的 kind/规则静默丢弃 |
| 规则声明降级 | yml 的 `scope_rules: … → downgrade` | 仍报、不扣分 |

9 个标记覆盖敏感 / 质量 / 函数长度 / 复杂度 / 体积 / 语法 / 残留 / 风格 / i18n 类，`lib/exempt/index.js` 是唯一判定入口；finding 的 `exemptHint` 会指明该用哪个标记，且保证「提示的标记写下去真能生效」。文档类文件（`.md/.txt/.rst` 及 `docs/` 下）里的硬编码绝对路径降级为 warning，其余一律 blocker。

## 七、自家纪律与审计规则的边界

规则对**任何**仓库生效。像「一次提交=一个小版本」「版本号必须 1 开头」这类只适用于本机自研项目的纪律写进规则，必然在第三方仓库大面积误报——这类约定放 skill 与版本纪律，不固化成审计规则。版本号的权威口径是 SemVer 2.0.0：0.x 是合法开发期，1.0.0 才是稳定线（见 `skills/workflow/versioning-rule.md`）。

第三方项目命中多不等于代码有问题；判别时先问「规则说的事实成立吗」，再决定修代码还是修规则。

## 八、扩展方式

新增一条规则的最小路径：yml 加条目 → 需要精筛就写 `lib/ast/*` → 在 `lib/checks/common.js` 接线 → 双向样本测试 → 跑全量回归。新增一个语言槽位：建 `audit-rules-<lang>.yml` 并设 `exts`，同时让 nodejs 对应规则移除该扩展名（让位），避免双报。

## 九、与 UI 的关系（2026-11-08 解耦）

审计 Tab 已从设置页移出：客户端分片归档在 `lib/client-parts/audit/`，**不参与构建**，
产物 `lib/client.js` 里不再有审计 UI。页面现为两选项卡（账号信息 / 设置）。

这不影响审计能力——后端引擎、提交门禁、`code_audit` 等工具、HTTP 接口、
审计设置键全部照常运行。设置页不再提供审计开关与权重编辑入口，需要时改
`<DSH_HOME>/git-push/config.json` 的对应键（键名见 `docs/SPEC.md` 设置键表）。

为什么这样拆：审计与 git 侧计划重构成两个独立项目，先把**文件边界**划清
（分片分目录、设置键单独成文件），行为保持不变，将来拆包时整体搬走即可。

## 边界与注意

- 规则字段、豁免标记、动态权重的完整速查见 `docs/DETAILS-EXEMPT-AND-RULES.md` 与 `docs/功能-审计规则体系.md`。
- 审计不改代码；修复永远是改代码或修规则，不是给自己加豁免。
- `full` 默认有扫描文件上限，超出会截断并在结果里提示「本次只扫了前 N 个文件」。
