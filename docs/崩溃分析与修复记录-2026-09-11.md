# dsh-git-push 崩溃分析与修复记录

> 日期：2026-09-11 ｜ 事件：dsh-git-push v1.0.4（link 到本工作区）反复导致 DSH 实例启动后崩溃退出
> 结论：累计修复 5 处 cordis 兼容性 bug；最终按用户要求先整体禁用插件（patch 层 `disabled: true`），源码与修复保留在本工作区。

---

## 一、现象

- DSH 实例（端口 30801）启动**数秒到数十秒后崩溃退出**，反复复现。
- 日志模式：启动 banner 正常打印后，插件树加载阶段抛错，`[!] DSH 退出 code=1 signal=null`。
- 错误逐轮变化（每修一个暴露下一个），共 5 种：

| # | 错误 | 崩溃点 |
|---|------|--------|
| 1 | `Cannot read properties of undefined (reading 'validate')` | `vendor/cordis/src/fiber.ts:53` — Config 校验 |
| 2 | `cannot get property "log" without inject` | `lib/index.js` apply 内 |
| 3 | `cannot get property "workspaceRoot" without inject` | `lib/index.js` apply 内 |
| 4 | `Invalid effect` | cordis fiber — apply 返回值 |
| 5 | `cannot get property "slots" without inject` | 客户端 `client.js` |

另有一次「启动成功后被 SIGTERM 杀掉」：日志显示 token 已正常生成、无任何报错，随后收到外部 SIGTERM。排查确认 **guardian systemd 服务为 inactive（路径已失效），非本插件引起**；日志 `smbd_audit` 显示同期有 SMB 会话在插件目录执行过依赖安装（创建 `node_modules/@deepseek-ai/cosmokit`、`schemastery` 等），可能扰动运行中实例（SIGTERM 具体来源未完全坐实，但插件树本身已加载成功）。

---

## 二、根因分析（cordis 插件契约）

DSH 插件运行在 Cordis 容器里，第三方源码插件必须满足 5 条契约，否则加载即崩：

### 1. Config 必须是 Standard Schema v1（带 `~standard` 标记）

Cordis 的 `resolveConfig` 会读 `Config['~standard'].validate(config)`。若 `Config` 是普通对象字典（无该标记），`Config['~standard']` 为 undefined，读取 `.validate` 直接抛 `TypeError`。

```js
// ❌ 崩溃：普通对象
export const Config = { enabled: true, workspaceRoot: '' };

// ✅ 合规：schemastery 的 Schema.object（自带 ~standard）
import Schema from '@deepseek-ai/schemastery';
export const Config = Schema.object({
  enabled: Schema.boolean().default(true),
  // ...
});
```

本插件历史版本还内置了「依赖降级」逻辑：`require('@deepseek-ai/schemastery')` 加载失败时退到自写的 `makeFallbackSchema()`，而该降级 schema **原本不带 `~standard`**——恰好 SMB 会话动过依赖后触发降级路径，复现崩溃①。
**修复**：`lib/index.js` 的 `makeFallbackSchema().object()` 返回值补上 `~standard.validate`（透传校验），双路（真实 schemastery / 降级）都稳。

### 2. `ctx.xxx` 服务属性必须先 `inject` 或 `ctx.get()`

Cordis 里 `ctx.log`、`ctx.workspaceRoot` 等是**服务属性**，未在 `inject: [...]` 声明时直读会抛：

```
cannot get property "log" without inject
```

```js
// ❌ 崩溃：直读服务属性
const log = ctx?.log;

// ✅ 合规：可选依赖用 ctx.get()
const log = ctx?.get?.('log');
const workspaceRoot = ctx?.get?.('workspaceRoot');
```

**修复**：`lib/index.js` apply 内两处，`ctx?.log` → `ctx?.get?.('log')`、`ctx?.workspaceRoot` → `ctx?.get?.('workspaceRoot')`。
> 甄别陷阱：`ctx.errors` 等**自建函数参数**（如 `safeRe(pattern, label, errors)` 恰好把参数命名为 `ctx`）不是 cordis 的 ctx，无需改——实例能正常运行即为佐证。

### 3. `apply()` 返回值只能是 disposer / Promise / undefined

Cordis fiber 对 apply 返回值做类型检查，返回普通对象（如 `{ ok: true, version, tools }`）抛 `Invalid effect`。

```js
// ❌ 崩溃：返回普通对象
return { ok: true, version, tools: count };

// ✅ 合规：返回 undefined（插件注册均走 ctx.inject，生命周期由 cordis 管理）
return;
```

**修复**：`lib/index.js` apply 尾部改为 `return;`（保留说明注释）。

### 4. 客户端半部 `ctx.slots` 同样要 inject

客户端插件（`client.js`，经 `package.json` 的 `dsh.client` + `exports["./client"]` 自动发现）里用 `ctx.slots` 注册设置卡片时，同样要求声明注入：

```js
// ❌ 崩溃：client 端直读 ctx.slots
function apply(ctx) { ctx.slots.inject('settings.plugin.item', ...); }

// ✅ 合规：声明并导出 inject（与 dsh-web-network-optimizer 一致）
const inject = ['slots'];
function apply(ctx) { ctx.slots.inject('settings.plugin.item', ...); }
exports.inject = inject;
```

**处理**：2026-09-11 先**临时注释** `client.js` 的 slots 注册段（副作用：设置页不显示 git-push 卡片；工具/审计/推送功能不受影响），避免客户端加载失败反复拖垮实例。

### 5. 依赖解析与安装纪律

- 插件通过 `link:` 装到 profile，软链指向本工作区（`node_modules/dsh-git-push -> ../../../../工作区/dsh-git-push-v2`），工作区源码修改**即时生效，无需重装**。
- **不要从 SMB 共享往插件工作区目录里执行 `npm/pnpm install`**：会把 `node_modules` 装进工作区、扰动 DSH 双锚点依赖解析（先查 bundle 目录再查 profile 目录），是本次反复崩溃的诱因之一。依赖应装在 profile 侧（`dsh plugin add` 自动管理）。
- 修改源码后务必核对**落盘成功**：曾因 SSH heredoc 传输 + `2>/dev/null` 吞掉 assert 错误，导致「改的是空气」，`node --check` 检查旧文件误报通过。应以 mtime 更新 + 内容 grep 双重确认。

## 五、经验沉淀

1. cordis 插件是「契约式加载」：Config 形态、ctx 注入、apply 返回值、client inject 四道关卡，任何一个不合规都会让整棵插件树失败。
2. `dsh-plugin-doctor.mjs`（DSH 安装根目录）已实现四类模式的一键扫描/修补/备份/重启验证，可复用于其他源码插件。
3. 判断「修好了」必须基于长时间观测（进程存活 + 端口 + 日志无 exit），不能只看启动前几行日志。
