# gitpush 与审计分家方案（2026-11-15 设计稿）

> 状态：**设计稿，未实现**。前置工作（引擎/CLI/HTTP/参数/消息/中间层五层解耦）已完成，
> 本文档描述**物理拆分**为两个 npm 包。
>
> 关系：`docs/2026-11-15-审计中间层与引擎声明分层方案.MD` 是「同库内分层」（已完成）；
> 本文档是它的下一步「拆成两个包」。

## 一、目标形态

| 包 | 形态 | 发布物 |
|---|---|---|
| **dsh-git-push** | DSH 插件（现有） | 只含 git 侧：git 操作 / 提交推送 / npm 发布 / 账户 / 仓库索引 / **调预处理的接口** |
| **审计包（新命名待定）** | **普通 npm 包**（**不是 DSH 插件**） | 三形态：① **library**（被 import）② **CLI**（被 spawn）③ **MCP server**（通用协议） |

**关键**：审计包**不注册 DSH 工具、不提供 DSH HTTP、不含 `cordis.patch.yml`**。
它通过 MCP 对外提供能力，任何 MCP 客户端（不限于 DSH）都能调用。

## 二、职责切分（豁免全归审计）

### 2.1 归审计包（判）

| 职责 | 说明 |
|---|---|
| 引擎适配 | 内置引擎 / 第三方引擎（eslint、semgrep…） |
| 检查器与规则 | `ast` / `checks` / `rules/*.yml` |
| **代码标记豁免** | `dsh-skip-*`、`eslint-disable-next-line`、`nosemgrep`、`# nosec`、`.gitleaksignore` |
| **目录豁免** | 示例目录（`audit-samples/`）、测试夹具目录 |
| **私有库豁免** | 拿到 `visibility` 后，「private ⇒ 只报告不拦截」的判定 |
| **临时豁免** | `exemptPaths` / `exemptReason`（调用方传入，审计侧判） |
| 评分 | dims / 权重 / 扣分曲线（引擎声明 dims，中间层算） |
| **拦截判定** | 综合上述豁免后输出 `blocked` 列表与 `blocked: true/false` |

### 2.2 归 gitpush（探 + 用结论）

| 职责 | 说明 |
|---|---|
| **探可见性** | `resolveRepoVisibility()` —— 需要 GitHub token 与网络，属 git 侧能力 |
| **探 repo 上下文** | 仓库路径、分支、origin、改动集 |
| 调审计 | 通过 CLI（`preCommit.command`）或 MCP |
| 用结论 | 拿到 `blocked: true` ⇒ 拒绝提交；`false` ⇒ 继续 commit/push |
| git 侧的一切 | clone / push / npm publish / 账户 / 索引 |

### 2.3 一句话原则

> **「探」留 gitpush，「判」归审计。**
>
> 例：私有库豁免 —— 探 `visibility` 需要 GitHub 认证（gitpush 有），
> 但「private 只报告不拦截」这个**判定**归审计（它拿到 `visibility` 自己判）。
> 否则审计包会被逼着实现 GitHub 认证，就不可能"通用"了。

## 三、审计包的三种形态

### 3.1 library（被 import）

```js
import { audit, score, resolveExemptions } from '<审计包>';

const result = await audit({
  repoPath, scope: 'diff' | 'full',
  visibility: 'private' | 'public' | 'unknown',   // 由调用方探好传入
  exemptPaths: [], exemptReason: '',
  rulesetDir, weights,
  engine: 'builtin' | 'eslint' | …,               // 可选，缺省内置
});
// → { ok, scope, summary, quality, findings, blocked, exempt, files, engine }
```

### 3.2 CLI（被 spawn）

```
<审计包 bin> --repo <path> --scope diff|full
             [--visibility private|public|unknown]
             [--exempt-paths a,b] [--exempt-reason <r>]
             [--ruleset <dir>] [--weights <json>]
             [--engine builtin|eslint|…] [--blockers-only] --json
```

**契约**（沿用现有，只增 `--visibility`）：

```
stdout : 单行 JSON { ok, scope, summary, quality, findings, blocked, exempt, files, engine }
exit   : 0 = 无 blocker（放行）｜1 = 有 blocker（事实，拦截由调用方用结论）｜2 = 执行失败
```

> 注意：拆包后 exit 1 的语义要更小心 —— 既然拦截判定也在审计侧，
> 那 `blocked` 字段就是权威结论，`exit 1` 只是它的镜像。调用方读字段，别只读退出码。

### 3.3 MCP server（通用协议）

原有的 DSH 工具**改为 MCP tools**，任何 MCP 客户端可调：

| 原 DSH 工具 | MCP tool | 说明 |
|---|---|---|
| `code_audit` | `audit` | 审计仓库/文件 |
| `io_scan` | `io_scan` | I/O 风险扫描 |
| `link_check` | `link_check` | 文档链接检查 |
| `scope_check` | `scope_check` | 拼接产物作用域撞名 |
| `exempt` | `exempt_hint` | 豁免标记查询/检查 |

**收益**：审计能力不再绑 DSH —— Claude Desktop / Cursor / 任何 MCP 客户端都能用。
**代价**：这些工具在 DSH 里不再以"插件工具"形式出现，需通过 MCP 挂载（DSH 支持 MCP 连接）。

## 六、兼容与过渡

| 问题 | 方案 |
|---|---|
| **不装审计包就没审计？** | gitpush 的 `optionalDependencies` 带审计包，或首次运行时提示安装；`preCommit.command` 缺省指向它 |
| **旧配置里的 `preCommit.command`** | 继续有效（指向什么都不影响 gitpush 侧） |
| **DSH 里的 `code_audit` 工具消失** | 过渡期保留壳（内部转 MCP）；或直接下线并在 README 说明改用 MCP |
| **审计 HTTP 端点（`/api/git-audit/*`）** | 跟着审计包走（若审计包提供 HTTP）或下线（改用 MCP） |
| **两个包的版本关系** | 互相独立；gitpush 只依赖**契约**不依赖版本号 |

## 七、风险

| 风险 | 程度 | 缓解 |
|---|---|---|
| **拦截判定的迁移最容易出错**（豁免全搬走后 gitpush 只剩"用结论"） | **高** | 迁移前后用同一批量样本比对 `blocked` 列表逐条一致 |
| `visibility` 探不到时的语义（现在 unknown ⇒ 保守拦截） | 中 | 契约里明确 unknown 的处理，别让两包各猜一套 |
| MCP 化后 DSH 侧的工具体验变化 | 中 | 过渡期保留工具壳 |
| 两包同时改动时的联调成本 | 中 | 契约测试（各包独立跑 + 跨包集成测试） |
