# 审计中间层与引擎声明分层方案（2026-11-15 设计稿）

> 状态：**设计稿，未实现**。目标是把「豁免 + 评分」从审计引擎里抽出来，做成**同库内的独立中间层**；
> 引擎（自研与第三方一视同仁）只负责**产出 findings + 声明评分标准**。
>
> 约束：**中间层与审计层是同一个库**（代码内分层，不是拆成两个项目/两个进程）。

## 一、目标

| 层 | 职责 | 不做什么 |
|---|---|---|
| **git 侧** | 只调一个「预处理」动作 | 不 import 任何审计实现、不知道评分/豁免细节 |
| **中间层**（同库内） | ① 管豁免 ② 按引擎声明的标准算分 ③ 适配不同引擎 | 不做代码判定（那是引擎的活） |
| **审计引擎**（自研/第三方） | ① 扫代码产 findings ② 声明 scoreSpec | **不算分、不管豁免** |

**一句话**：把豁免与评分做成防腐层，换引擎时用户的豁免习惯与评分口径不变。

## 二、现状证据（为什么这个切法是干净的）

### 2.1 评分与豁免都只依赖 findings 的数据形状

```js
// lib/score/index.js:127
scoreQuality(findings, weights, context)   // 只吃 findings 数组 + 权重 + 文件数统计

// lib/exempt/index.js
exemptForFinding(finding, text)            // 只吃 finding 对象 {severity, rule, file, line, message}
```

两者都**不依赖"谁产出的 findings"** ⇒ 技术上可以搬进中间层。

### 2.2 `scoreQuality` 已经有 5 个调用点（说明它本就该是共用层）

| 调用点 | 场景 |
|---|---|
| `scripts/audit-gate.mjs:161` | 提交前预处理（引擎子进程内） |
| `lib/app/tool-call.js:528` | `code_audit` 工具 |
| `lib/app/audit-api.js:130` | HTTP `/audit` 聚合 |
| `lib/audit/history.js:75` | 历史提交审计 |
| `lib/cli/commands-audit.mjs:91` | `audit-sluice audit` |

### 2.3 `DEFAULT_WEIGHTS` 现在在评分层（`lib/score/index.js:10`）

**这是本次要动的归属**：权重是**引擎的评分标准**，不该由中间层硬编码。自研引擎要把它作为自己的 `scoreSpec` 声明出去。

## 三、目标结构（同库内分层）

```
lib/
├── preprocess/                  ← 中间层（本方案新增的组织层）
│   ├── index.js                 统一入口：适配 → 豁免 → 评分 → 汇总
│   ├── adapters/
│   │   ├── builtin.js           自研引擎适配：调 lib/audit，拿 findings + scoreSpec
│   │   └── eslint.js            （将来）第三方适配 + 豁免声明采集
│   ├── exempt.js                豁免：自家标记 + 目录豁免 + 第三方标记映射
│   └── score.js                 评分：用 scoreSpec + 用户权重覆盖
│
├── audit/                       ← 自研引擎（只产 findings + 声明 scoreSpec）
│   ├── index.js                 扫代码 → findings
│   └── score-spec.js            ★ 新增：DEFAULT_WEIGHTS 从 lib/score 搬到此处，作为引擎声明
│
├── score/                       ← 保留为「评分的纯函数实现」（被 preprocess/score.js 调用）
└── exempt/                      ← 保留为「豁免的纯函数实现」（被 preprocess/exempt.js 调用）
```

**关键**：`lib/score` / `lib/exempt` **不删**，它们是最底层实现；`lib/preprocess/*` 是**编排层**（决定用谁的声明、怎么合并、怎么映射）。这样迁移风险最小——底层不动，只加编排。

## 四、三个契约

### 4.1 统一 finding 形状（中间层的输入）

```js
{
  file: string,
  line: number,
  rule: string,                            // 规则 id（如 'performance/busy-wait-loop'）
  severity: 'blocker' | 'warning' | 'notice',
  message: string,
  dim?: string,                            // 归属维度；缺省时中间层按 rule→dim 映射表推断
  source?: 'builtin' | 'eslint' | 'semgrep',  // 溯源（豁免映射要用）
}
```

### 4.2 scoreSpec（引擎声明评分标准）

```js
{
  dims: [
    { id: 'security',   weight: 18 },
    { id: 'robustness', weight: 15 },
    // …
  ],
  // 可选：该引擎自带的「维度判定」（某条 finding 属于哪个 dim）
  dimOfRule?: (rule) => string | undefined,
  // 可选：说明性字段（展示用）
  note?: string,
}
```

**明确不开放**：扣分曲线（`k` 值、对数衰减公式）**不交给引擎**。
理由：一旦引擎能定制曲线，「换引擎分数口径就变」，与本方案初衷相反。曲线永远是中间层统一的。

### 4.3 豁免映射（第三方引擎的关键）

中间层维护 `EXEMPT_MAPPING`：

| 引擎 | 豁免写法 | 映射策略 |
|---|---|---|
| 自研（builtin） | `// dsh-skip-*`（行内/文件头）、`.auditignore`、目录豁免 | 原生 |
| ESLint | `/* eslint-disable-next-line rule */`、`/* eslint-disable rule */` | **声明式优先**：读 ESLint 的 `suppressedMessages`；不支持时退回读取源码标记 |
| Semgrep | `// nosemgrep` | 读取源码标记 |
| Bandit | `# nosec` | 读取源码标记 |
| gitleaks | `.gitleaksignore` | 读取文件 |

**两种策略并存**（B 优先 + A 兜底）：

- **策略 B（声明式）**：引擎自己输出"哪些 finding 被它豁免了" ⇒ 中间层直接采信（语义最准）
- **策略 A（读取式）**：中间层自己扫源码里的第三方标记 ⇒ 转换成自己的豁免判定（通用，任何引擎都能用）

适配器要声明自己是 B 还是 A：`adapter.supportsSuppressed = true | false`。

## 五、自研引擎改造（本次核心动作）

### 5.1 现在

```js
// scripts/audit-gate.mjs:161（引擎子进程内）
const auditResult = await auditWithScope(repo, opts);
const quality = scoreQuality(auditResult.findings, opts.weights, {…});   // ← 引擎自己算分
return { ok, summary, quality, findings, files };
```

### 5.2 改后

```js
// 自研引擎（lib/audit）只产出两样
export function runBuiltinAudit(repo, opts) {
  const raw = await auditWithScope(repo, opts);
  return {
    findings: raw.findings,
    files: raw.files,
    scoreSpec: getBuiltinScoreSpec(),      // ← 从 lib/audit/score-spec.js 读
  };
}

// 中间层算分
const { findings, scoreSpec } = runBuiltinAudit(repo, opts);
const quality = middleLayer.score(findings, scoreSpec, userWeights, { files });
```

### 5.3 `lib/audit/score-spec.js`（新增）

```js
// DEFAULT_WEIGHTS 从 lib/score/index.js 搬到这里——它是「自研引擎的评分标准声明」
export const BUILTIN_DIMENSIONS = [
  { id: 'readability',   weight: 15 },
  { id: 'maintainability', weight: 15 },
  { id: 'robustness',    weight: 15 },
  { id: 'security',      weight: 18 },
  { id: 'performance',   weight: 10 },
  { id: 'coverage',      weight: 10 },
  { id: 'observability', weight: 5 },
  { id: 'deployability', weight: 5 },
  { id: 'docs',          weight: 4 },
  { id: 'dx',            weight: 3 },
];
export function getBuiltinScoreSpec() {
  return { dims: BUILTIN_DIMENSIONS, dimOfRule: dimOfRuleBuiltin, note: '自研审计引擎' };
}
```

**兼容**：`lib/score/index.js` 仍导出 `DEFAULT_WEIGHTS`（供中间层**兜底**用：引擎不声明时用这套），但**自研引擎的声明以 `score-spec.js` 为准**——两者内容一致，避免漂移需要一条测试钉住。

## 六、5 个调用点如何收敛

| 调用点 | 改法 |
|---|---|
| `scripts/audit-gate.mjs` | 引擎子进程**不再算分**；输出 `{ findings, scoreSpec, files }`，由调用方（中间层）算（若仍要子进程，则中间层逻辑也在子进程内，见 §七） |
| `lib/app/tool-call.js` | 经 `preprocess.score()` |
| `lib/app/audit-api.js` | 同上 |
| `lib/audit/history.js` | 同上（历史审计也是"引擎产 findings + 中间层算分"） |
| `lib/cli/commands-audit.mjs` | 同上 |

## 七、进程边界（要你确认，见 §九）

本方案默认：**中间层与引擎同库同进程**。因此有两种可能形态：

- **形态 1（推荐）**：`audit-gate.mjs` 子进程内包含「引擎 + 中间层」→ git 侧只拿到最终结果（已算分、已豁免过滤）
  - 优点：git 侧最简单；中间层与引擎零跨进程开销
  - 缺点：中间层代码随引擎子进程一起被 spawn（多加载 ~1s，可接受）
- **形态 2**：git 侧进程内跑中间层，引擎仍是子进程 → 中间层要跨进程拿 `findings + scoreSpec`
  - 优点：中间层可被 git 侧其他路径复用（如 HTTP `/audit` 不必再起来）
  - 缺点：多一层数据传递（findings 可能几千条）

## 八、边界（本方案不做什么）

1. **不拆成两个项目/两个 npm 包**（用户明确：同一个库）
2. **不开放扣分曲线定制**（否则换引擎分数口径就变）
3. **不重写 `lib/score` / `lib/exempt` 的底层实现**（只加编排层，迁移风险最小）
4. **不改变用户可见的豁免语法**（`dsh-skip-*` / `.auditignore` 照旧）
5. **本次不实现**（本文档只是设计稿）

## 九、待确认项

1. **进程形态选 1 还是 2**（见 §七）
2. **第三方引擎的 severity 映射**：ESLint 只有 error/warn，怎么落到 blocker/warning/notice？
   - 建议：error→blocker、warn→warning；notice 由引擎额外声明（ESLint 没有）
3. **`dimOfRule` 的默认映射表放哪**：中间层（通用）还是引擎（各自声明）？
   - 建议：引擎声明优先；中间层保留一份「通用兜底映射」（按 rule 前缀推断，如 `security/*`→security）
