## 二、逐维度详评

### 1. 可读性 6.5 / 10

亮点（符合 yaml good 清单）：
- 每个文件顶部有职责头注释；函数命名全部动词短语（`resolveValidGitToken` / `ensureNpmIgnored` / `probeTokenValid`），几乎无缩写滥用。
- 关键坑位注释详实（CIFS filemode、quotepath、空 blob、双副本 token），可读出真实工程经验。

不足（对照 yaml bad 清单）：
- 用插件自己的 `checkFunctionLength`（50/100 阈值）全量复扫 lib，命中 16 个超标函数：
  - `lib/index.js:82` `apply()` **1148 行**（blocker）——设置注册、注释注入、事件监听、14 个 HTTP 端点、11 个工具注册全部在一个函数体里；
  - `lib/core.js:827` `commitAndPush` 214 行、`lib/audit.js:338` `auditFile` 213 行、`lib/core.js:382` `pushViaApi` 112 行、`lib/core.js:1665` `rebuildHistory` 80 行等。
  - yaml「单函数 ≤50 行（硬上限）」大面积失守，且这些存量函数永远不会被提交门禁发现（见可维护性第 3 条）。
- 历史溯源注释（【原代码】/【改为】/【思路】三段式）密度过高，新人要在新旧实现之间来回跳；`lib/core.js:1214-1216` 还存在连续三段重复 JSDoc。
- 大量业务语义靠中文措辞正则表达（comment-wording、docs-conversation），规则含义藏在 `rules.js` / `audit.js` 两处，需要交叉对照才能理解审计行为。

### 2. 可维护性 6 / 10

亮点：
- 分层意图明确：`core.js`（纯函数不依赖 ctx）/ `audit.js` / `quality.js` / `rules.js` / `permit.js` / `repo-index.js` / `env-inject.js` / `viewer.js` / `client.js` 各司其职，多数可独立单测。
- 配置面集中（`cordis.patch.yml` + 设置页 scope.watch 即时生效），改动入口清楚。

不足：
- `core.js` 2714 行承担至少六个职责：git 执行封装、GitHub API、token/SSH 探测、User 仓选址评分、clone/模板落地、历史重建与 README 生成——应拆 `git.js` / `github-api.js` / `token.js` / `user-repo.js` 等。
- `resolveGitToken`（core.js:1960）与 `resolveValidGitToken`（core.js:2028）各自维护一份约 30 行的候选清单复制品，改一处漏一处的风险真实存在——正是 yaml bad「同一段逻辑复制一份以上」。
- User 仓选址评分是魔法数字叠加（+1000/+800/+500/+300/+60…，core.js:2292 `scoreUserRepo`），1.36.0 与 1.36.2 两次补丁都在改权重，规则演进靠叠补丁而非显式策略表。
- 提交门禁只审计「本次变更文件」：hardcode 规则有 `hardcodeFullScan` 全量开关，但 func-lines / silent-catch / sync-in-async 等质量规则没有全量模式——**存量代码永远不体检，审计工具对自身 16 个超大函数失明**。

### 3. 健壮性 7 / 10

亮点：
- 错误处理风格统一：几乎全部返回结构化 `{ ok, error }` 而非抛出；permit 状态写盘用 tmp+rename 原子替换；全链路支持 `dryRun`。
- 降级链路完整：token 401 → SSH 回退；API 失败 → SSH 回退；分支名不符 → 远端 default_branch 免疫；空 blob 判定以退出码为准；可见性探测失败保守不豁免。

不足：
- 静默吞错规模大：lib 全部 `catch` 约 149 处，其中无错误变量形态 `catch {` 80 处（core.js 独占 46）。多数只有一行「跳过」注释——yaml bad 清单第一条（静默吞错）实质命中，而插件自带的 `checkSilentCatch` 只识别单/双行形态，全库只报出 2 处，**检测器与真实形态脱节**。
- 实测崩溃：`test/test-core.mjs` 在本仓运行到 `persistGithubToken` 时抛 `EROFS` 未捕获——`resolveUserDir` 全池比对选中了只读的真实同级仓，`persistGithubToken` 内部 `writeFileSync` 直接把异常抛到测试顶层。在只读卷/异常卷上该路径会让整个调用方崩掉而非优雅降级；同时暴露测试夹具会写到临时目录之外（污染真实 User 仓选址）。
- `test/test-apply.mjs` 因 `@deepseek-ai/dsh-tools` 解析失败直接 ERR_MODULE_NOT_FOUND——依赖未声明使 apply 层在宿主环境之外完全不可运行（见可部署性）。
- `getDiff` 把 untracked 文件按 utf8 读入合成 diff，二进制新文件会读出乱码行进入审计（`isBinary` 未对 untracked 生效）。

### 4. 性能 5 / 10

不足（对照 yaml「批量任务不堵死单进程」）：
- 子进程全部同步：spawnSync/execSync 共 31 处、同步 fs 调用 166 处（core.js 95 处），并且直接跑在 HTTP handler 主线程里：
  - `getCommitHistory`（viewer.js:48）是 O(提交数×文件数) 次子进程——100 提交 × 10 文件 ≈ 2000+ 次 spawn，单次 10-40ms，一次 `/api/git-push/commits` 请求可把事件循环阻塞数十秒；limit 上限 500 时更甚。
  - `readRepoStatus` 单仓 6 次串行 spawn（branch/remote/rev-parse/status/log + isRepoEmpty 的 rev-list），`scanRepos` 每次请求全量重扫，`resolveViewerRepo` 每个 diff 请求都重新扫全部仓库。
- 缓存极少：仅 env 注入 60s、tokenValid 60s 两处；`buildRepoIndex` 对每仓串行 await GitHub 可见性查询，无并发无缓存。
- `readJson`（index.js:764）无 body 大小上限，无限拼接内存。

亮点：
- `pushViaApi` 有内容级短路（tree sha 相同不重推）与远端 blob sha 复用，避免重复上传；这是真正考虑过 API 成本的设计。

### 5. 安全性 7.5 / 10

亮点（对照 yaml good 清单覆盖较好）：
- token 全链路不回传明文、掩码显示（`maskToken`）；凭据文件 0600；token 格式前缀校验。
- `githubFetch` 硬闸 hostname 必须为 api.github.com、`redirect: 'manual'` 拒绝跟随 302（防 tarball 跳第三方域）。
- viewer 端零写操作；commitId 白名单正则；`esc()` 转义后渲染；repo 参数只认扫描清单精确匹配。
- 自带 secret / credential-file / hardcode-path / docs-conversation 门禁并在本仓实际生效（本次 code_audit passed）。

不足：
- **全部 `/api/git-push/*` 端点无鉴权**：`POST /api/git-push/commit`（可触发提交推送）、`/rebuild`（破坏性历史重建）、`/gen-ssh-key`、`/account-check` 仅依赖宿主进程绑定本机端口兜底。yaml「敏感接口即使无密码也拒绝」未满足；一旦部署形态变化（反向代理/容器端口映射）即成暴露面。
- `readJson` 无大小限制（与性能同源）。
- token 探测面过宽：递归扫 HOME/DSH_HOME 的「会话/sessions/workspace」子目录找 `.git-push-token`、读 data/sensitive——容错性强，但「任何同名文件即被采信」与凭据最小读取原则冲突；`resolveGitToken` 与 `resolveValidGitToken` 双轨也放大了这个面。
- 启动时直接写宿主机全局 git config（`core.filemode=false`、`safe.directory=*`）——放宽了全机 git 属主校验，属于超出插件边界的全局副作用，且无配置开关。
- SSH known_hosts 采用 `StrictHostKeyChecking=accept-new`（TOFU），首次连接不校验指纹。

### 7. 可观测性 6.5 / 10

- 优点：统一 `ctx.logger('git-push')`（lib 内无散落 console 输出）；启动与关键动作 info、降级 warn；返回结果带 `steps[]` 逐步留痕（npm-ignore/add/commit/skip-commit）；permit 状态落盘 `lastAttempt` / `lastAutoPush` 可回查；审计 findings 带 file+line 定位。
- 不足：无 requestId/trace 贯穿一次提交链路（多仓自动推送时无法按请求聚合日志）；HTTP 错误统一 500+`e.message`，无错误码枚举；无 /health、/metrics 端点（`/api/git-push/status` 算半个健康检查但无运行指标）；80 处静默 catch 意味着大量降级「无人知晓」，排障只能靠重跑复现。

### 8. 可部署性 7 / 10

- 优点：纯 ESM、零第三方运行时依赖；路径全部环境推导（DSH_HOME/HOME/cwd），1.36.1 专门清除了写死本机卷的存量路径；CIFS/只读卷兼容（/tmp 中转建仓、filemode 处理）极为用心；User 仓缺失时模板自动落地，首次部署零手工步骤；设置页改动即时生效无需重启。
- 不足：`package.json` **无 dependencies / peerDependencies / engines 声明**——对新环境不友好（宿主外 npm i 后 peer 包解析失败，test-apply 崩溃即实证）；无构建/发布脚本（发布靠手工 bump version + git tag）；部署即修改宿主机全局 git config，回滚插件不会还原；无容器化/版本化部署说明（可部署性依赖宿主 DSH 运行时这一前提未在包元数据里声明）。

### 9. 文档 8.5 / 10

- 优点：README 约 30KB 且与本日提交同步（git 元数据核实），按 yaml good 清单具备功能说明、版本表、用法与注意事项；`docs/code-quality-checklist.yaml` 是少见的「AI 可解析」评分标准；代码注释密度极高；skills/ 双仓文档体系完整，与插件注入机制闭环。
- 不足：文档视角偏向「变更史/决策记录」，缺一页纸的「贡献者上手」：如何跑测试（10 个文件、两种风格）、模块依赖图、各 lib 文件职责边界；docs/ 卫生欠佳——`1.js`（14 处 console 输出的演示脚本）与 3 份当日评估 md 混在文档目录且未入库；README 由 AI 面向 AI 编写，人类新手的第一入口体验一般。

### 10. 开发者体验 6.5 / 10

- 优点：11 个 agent 工具的 description 详尽到可直接正确调用（含参数语义、默认值、失败模式）；dryRun 普遍支持且语义一致；错误信息中文、结构化、带修复指引；测试夹具可直接复用；viewer 页面零外部资源可独立打开调试。
- 不足：无 `npm test` 一键入口；两种测试风格并存；无 lint/format 配置（本仓内无 oxlint/eslint 配置文件）；改 index.js/core.js 需在 1000-2700 行里定位上下文，改动影响面靠人脑推演；破坏性操作（rebuild/force）的安全闸依赖调用方自觉传参（工具描述里写了，但代码层 `git_rebuild_history` 的 force 仅要求布尔真值，无二次确认机制）。

## 三、不足清单（按优先级）

P0（建议尽快处理）：
1. `/api/git-push/*` 全端点无鉴权，含可破坏历史的 `/rebuild` 与可触发推送的 `/commit`（lib/index.js:791 起）。
2. 同步 git/fs 跑在 HTTP 主线程：`getCommitHistory` O(n×m) 次子进程、`scanRepos` 每请求全量重扫——一次页面操作可冻结整个 DSH 进程（lib/viewer.js:48、lib/core.js:546/591）。
3. `package.json` 未声明 peer 依赖与 engines：宿主外不可运行，test-apply.mjs 直接加载失败。

P1（还技术债）：
4. 拆分 `apply()`（1148 行）与 `core.js`（2714 行/六职责）；16 个超 50 行函数是 yaml 硬上限的成批违规。
5. 治理约 80 处 `catch {` 静默吞错，同时升级 `checkSilentCatch` 识别多行形态，避免检测器失明。
6. 建立一键测试（`npm test`）+ CI；统一测试风格；修复 test-core 对真实 User 仓的选址污染（夹具必须完全封闭在临时目录）。
7. `resolveGitToken` / `resolveValidGitToken` 候选清单抽成单一函数，消灭双份维护。

P2（改善项）：
8. `readJson` 加 body 大小上限；`readRepoStatus`/`scanRepos` 加短 TTL 缓存或合并 spawn。
9. token 探测范围收敛为显式配置优先、扫描兜底需开关；`safe.directory=*` 全局副作用改为可配置。
10. 质量审计增加「全量扫描模式」（func-lines/silent-catch/sync-in-async 也支持 hardcodeFullScan 同款开关），让工具能给存量代码体检。
11. docs/ 目录清理：演示脚本 `1.js` 与多份评估文档归档或入库，README 增补「贡献者：如何跑测试」一节。

## 四、加分项（值得保持的设计）

- `githubFetch` 的 api.github.com 硬闸 + 拒绝 302，把「域名纪律」做成了机器闸而非约定。
- token 401 → SSH 回退、分支名免疫、空 blob 以退出码判定、API 推送后手工维护 remote-tracking ref——全是真实踩坑后的修复，注释里可追溯。
- `pushViaApi` 内容级短路与 blob sha 复用，对 API 配额友好。
- dryRun 语义全链路一致；`ensureCustomIgnored` 的幂等 + 已跟踪解除跟踪处理正确。
- 审计门禁自产自用：本仓提交必须过自己写的 L0 审计，规则即文档。
- 双副本 token 探测（v1.36.2）这类「真实环境脏数据」问题的修复思路（格式+长度启发式 → 异步真校验）质量很高。

## 五、结论

按 yaml 的 rule_of_thumb（「扔给一个水平一般的新人，看完代码、跑完测试、改完功能，不引入新 Bug」）检验：**模块划分与注释能帮新人快速建立地图（B 水平），但跑测试这一步就会在 test-core 崩溃、test-apply 无法加载上卡住，巨型函数让「改完功能」的成本陡增**。66.5 分、B-，与 yaml「60-79：可用但有技术债，建议逐步还债」的判定一致——优先还 P0 三项（鉴权、同步阻塞、依赖声明），即可在测试与安全两个维度拿到明显回升。
