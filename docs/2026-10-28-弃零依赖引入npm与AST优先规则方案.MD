# 弃零依赖引入 npm · AST 优先规则 —— 决策与流程

> 状态：**方案已定稿，待执行**。本文档记录决策依据、分期里程碑与以后要遵守的流程。
> 确立日期 2026-10-28。长期目标，分多轮完成。

## 一、背景

两条线在同一天撞上同一个结论：

1. **C# 审计**：一份外部 C# 规则集建议在本仓库落地评估时，实测出「正则命中」与「真实缺陷」差距极大
   （同一批文件，正则口径 43 命中，AST 口径 0 违规——43 条全在注释与 XML doc 里）。
2. **语言覆盖**：`java / php / rust / swift / kotlin / c / go` 的**规则包早已存在、收集白名单早已放行**，
   但**没有语法文件** ⇒ 这些语言的 AST 类规则一直走 token 级回退。C# 是第一个把该问题暴露出来的语言。

根因不是语法难取，而是**当初为守「零依赖」把资产手工 vendored 进仓库**，且只挑了 js/ts/py 三个
（体积考虑），后续加语言一直卡在体积预算上。

## 二、决策清单

| # | 决策 | 内容 | 依据 |
|---|---|---|---|
| **D1** | **放弃零依赖约束** | tree-sitter（运行时 + 各语言语法）与 js-yaml 改为 npm 依赖，不再手工 vendored | 2026-10-28 确立 |
| **D2** | **已入库包袱可删** | `assets/tree-sitter/*`（3.7MB，含 runtime 与 3 个语法）、`lib/vendor/js-yaml/js-yaml.mjs`（104KB）在依赖接通后从仓库移除 | 2026-10-28 确立 |
| **D3** | **规则以 AST 精筛为准入门槛** | 评估规则不看「正则命中多少」，看「精筛后剩余误报多少」；接不了 AST 的形态规则不落地 | 2026-10-28 确立；以正则命中数否决规则属方法错误，判据只能是精筛后剩余误报 |
| **D4** | **版本精确锁定，不用 caret** | `web-tree-sitter` 锁 `0.25.10`、`tree-sitter-wasms` 锁 `0.1.13`、`js-yaml` 锁 `4.1.0` | 实测 `web-tree-sitter@0.27.1` 与 `tree-sitter-wasms@0.1.13` 语法不兼容（`getDylinkMetadata` 处报空消息错误）；caret 会让未来一次 install 悄悄升版并全线失效 |
| **D5** | **取不到语法就回退，绝不硬失败** | 依赖缺失/加载异常 ⇒ 该语言走 token 级回退，审计整体继续（现状行为保留） | 审计是提交门禁的一部分，增强件坏了不能拖垮门禁 |
| **D6** | **Unity 等框架专有语义不做特化规则** | 不为特定项目/框架写针对性规则 | 既定「不做太针对的、按性价比」口径 |

### 为什么 D2 删包袱不等于 D5 会失效

删除 vendored 副本后，若依赖没装上，`import('js-yaml')` 会失败 ⇒ **规则加载是启动关键路径**，等于插件不可用。
两层保障：

- **装配期门禁**：`sync_plugin` 已内置依赖校验（回执 `deps.ok / deps.missing`），依赖装不上当场报红，不会带病部署；
- **运行期降级**：js-yaml 走 `import('js-yaml')` 失败时，规则加载抛**明确错误信息**（指出缺哪个包、如何补装），
  而不是静默返回 0 条规则——静默「没有规则」比报错更危险。

> 口径差异是有意的：tree-sitter 侧「可选增强，失败回退」，js-yaml 侧「必需件，失败必须响亮」。两者不可混同，
> 后续改动不得把 js-yaml 一并降级为静默回退。

## 三、可行性证据（全部实测，非推断）

### 3.1 npm 包能否取到所需文件

| 包 | 版本 | exports 情况 | 取用方式 | 结论 |
|---|---|---|---|---|
| `web-tree-sitter` | 0.25.10 | `.` → `./tree-sitter.js`（import） | `import('web-tree-sitter')`；wasm 目录经 `require.resolve` 取 dirname 后 fs 读字节 | ✓ 可行 |
| `tree-sitter-wasms` | 0.1.13 | **无 exports 字段** | 直接拼 `node_modules/tree-sitter-wasms/out/tree-sitter-<lang>.wasm` | ✓ 子路径自由解析 |
| `js-yaml` | 4.1.0 | `.` → `./dist/js-yaml.mjs`（import） | `import { load } from 'js-yaml'` | ✓ 与现用 vendored mjs 同一产物 |

### 3.2 部署环境确实会装插件依赖

profile `node_modules` 里已有其他插件的运行时依赖落地为证：`sub2api-mcp`（由 dsh-plugin-sub2api 声明）、
`katex`、`playwright-core`（由 dsh-browser-service 声明）。本插件声明依赖后同样会被安装，
并由 `sync_plugin` 的 deps 校验把关。

### 3.3 语法 ABI 兼容（关键，决定能不能直接换源）

9 个语言各自喂真实形态样本，用现有 `lib/ast/treesitter.js` 的 runtime 加载解析：

| 语言 | 体积 | 节点数 | ERROR 节点 | 根节点 | 结论 |
|---|---|---|---|---|---|
| c_sharp | 3885 KB | 77 | **0** | compilation_unit | ✓ |
| java | 420 KB | 51 | **0** | program | ✓ |
| kotlin | 3958 KB | 43 | **0** | source_file | ✓ |
| go | 230 KB | 59 | **0** | source_file | ✓ |
| php | 794 KB | 38 | **0** | program | ✓ |
| rust | 800 KB | 39 | **0** | source_file | ✓ |
| swift | 3074 KB | 39 | **0** | source_file | ✓ |
| c | 774 KB | 37 | **0** | translation_unit | ✓ |
| cpp | 4554 KB | 33 | **0** | translation_unit | ✓ |

**9/9 可用、0 ERROR 节点** ⇒ `tree-sitter-wasms@0.1.13` 与锁定的 `web-tree-sitter@0.25.10` ABI 匹配
（本属同一批产物；此前探测 404 的原因是按 `csharp` 探测，真实语法内部名是 `c_sharp`）。

### 3.4 AST 带来的精度差（D3 的由来）

在真实 C# 语料（UmaViewer，668 个 `.cs` / 148,448 行）上对比：

| 候选规则 | 正则口径命中 | 精筛后真实缺陷 | 判定 |
|---|---|---|---|
| class 命名 PascalCase | 43 处 / 30 文件 | **0**（AST 见 11 个 class 声明全合规；43 处全在注释/XML doc） | 接 AST 后可落地 |
| 空 catch | 21 处 / 5 文件 | 21（抽查全为真 `catch { }`） | 高信号；且已有语言无关的 no-empty-catch，白名单一通即生效 |
| `.Result` 阻塞 | 6 处 | **0**（6/6 全是 `UnityWebRequest.Result.Success` 枚举成员访问） | 无类型信息必误报，**不落地** |
| magic-number（外部建议那条正则） | **7022 处 / 258 文件** | — | 满屏噪音，**不落地**；已有 `magic-number-smart` 带豁免 |
| SQL 拼接 / 反序列化 / 弱加密 | 0 处 | — | 本语料是 Unity 客户端无 DB/Web，**不能据此否决**（后端项目有价值），留待接 AST 后做 |
| `throw ex` | 4 处 | 形态明确 | 可落地 |

> 这张表是 D3 的依据：正则只是初筛，**以正则命中数否决规则是错的方法**，判据必须是精筛后剩余误报。

### 3.5 体积账（决定要不要按语言分档）

9 个语法：未压缩 **18,712 KB** → gzip **1,711 KB**（约 9%，wasm 压缩率极高）。

- 6 个中小语言（含 c_sharp）：约 636 KB gzip
- 3 个大个子（cpp 4.5MB / kotlin 4.0MB / swift 3.1MB 未压缩）：约 995 KB gzip
- 同时删掉 vendored 的 runtime + 3 语法（3.7MB）与 js-yaml（104KB）

净效果：**发布包 gzip 增量约 1.7MB 级别，同时换来 10 个语言有真语法树**；
按需下载需在 NAS 上引入运行时网络依赖与失败处理，性价比更差 ⇒ **全部入库**。

### M2 验收补记（lead 独立复验，非成员自报口径）

1. **扩大 `CODE_EXTS` 对自家评分零影响**：进程内开/关新增扩展名各跑一次全量审计，本仓库
   `889 = 889`、按规则增量集合为空——因为本仓库不含 C/C++/C# 文件。**结论：这处补齐不引入任何
   自库噪声**，成员原先「怕吵」的顾虑在自家仓库上不成立。
2. **隐私归属门禁必须走完整链路才可见**（探针口径教训，非缺陷）：直接 `auditFull(dir, {...})` 不传
   `ownership` 时隐私规则照跑（`auditFull` 设计上不自己探测归属，注入在 tool-call / audit-api / CLI 三处），
   据此会误判「归属门禁没生效」。走 CLI 端到端才看得到效果：同一 C# 语料 `blocker 13 → 8`，
   减少的正是 5 条 `secret-email`。**成员回报里的 `secret-email=5` 是 M2 当时的旧数据，当前链路下为 0。**
3. **分析覆盖率随之启动**：C# 进管道后该语料覆盖率 `0% → 2.9%`（连边 461 / 可解析调用 15668）；
   此前恒 0% 是因为根本没有代码文件进入解析。
4. `phtml` 保留：`TEXT_EXT`（早已在）、`EXT_TO_GRAMMAR`、`CODE_EXTS` 三处现已一致，删一处反而破坏同语言
   不同扩展名的对齐。

### M3 前置阻塞（收任何 C# 规则之前必须先修）

> **发布口径**：M1–M4 完成后一次性发布 **`dsh-git-push@2.12.3`**（tag latest，281 文件 / 打包 0.87MB）。
> 首次带运行时依赖发布，因此发布后做了三项独立复核：① `npm view dsh-git-push@2.12.3` 可查到、
> `npm pack @latest` 拿到 2.12.3；② 全新目录 `npm install` 后三个依赖按锁定版本落地
> （web-tree-sitter 0.25.10 / tree-sitter-wasms 0.1.13 / js-yaml 4.1.0）；③ 用包公开入口
> （`dsh-git-push/audit`，`exports` 只暴露主入口/`./audit`/`./client`）跑真实审计，
> 3 条 C# 规则（throw-ex / generic-exception / lock-on-self-or-type）在安装态全部命中。
> 注：刚发布后 `curl registry` 仍返回旧 latest，属 CDN/元数据缓存滞后，`npm view` 可见即可判定成功。

`security/no-repeated-hardcoded-literals` 在 C# **插值字符串** `$"…"` 上稳定误报（实测 10/41 ≈ 24%）：
提取器把 `{expr}` 插值段当成硬编码文本（例：`$"<error: {ex.Message}>"` 被提取为 `<error: {ex.Message}>`、
`$"{clip.name.Replace("/body","/facial")}_face"` 被提取为 `{clip.name.Replace(`）。根因是提取逻辑只认
JS 的 `template_string`，无 C# 插值串概念。**修法**：插值段整体排除在「文本」之外（与 JS 模板串同口径）。
此条不修，M3 收到的任何依赖字面量提取的 C# 规则都不可信。

**发布面提醒**：本仓库对 npm 只发 `dsh-git-push` 一个包；改依赖后 `npm install` 会真去拉 tree-sitter 包，
发布前需确认 registry 侧这三个版本可解析。

## 五、以后要遵守的流程（SOP）

### 5.1 新增一个语言的 AST 支持

1. 确认 `tree-sitter-wasms@<锁定版本>` 的 `out/` 里有该语法（**内部名可能带下划线**，如 `c_sharp`；
   探测用范围 GET `curl -r 0-0`，HEAD 会被 CDN 限流成假 404）。
2. 加进 `EXT_TO_GRAMMAR`（扩展名→语法名，注意一个语法可能服务多个扩展名，如 `kt` 与 `java`）。
3. 加进 `TEXT_EXT` 收集白名单（否则文件根本不进管道——这一步历史上漏过：php/swift 只补了规则包 yml
   没放行白名单，规则写了永远 0 命中）。
4. 跑**真机解析自检**：合成样本必须 0 ERROR 节点；再用真实项目语料抽几个文件复验。
5. 建对应 `audit-rules-<lang>.yml`（可为空占位——槽位由文件名自动发现，空占位也算接通，
   这是既定的「加载哪些语言 = 存在哪些语言规则包」口径）。
6. 全量回归 + 记录该语言命中数变化（有树前后的差异要留数据，作为后续规则取舍依据）。
7. **`EXT_TO_GRAMMAR` 的每个扩展名都必须在 `TEXT_EXT` 里**——这条已由 `test/test-treesitter-grammars.mjs`
   断言钉死（反向不设：白名单有、映射没有 = 合法走 token 级回退）。历史上「补了映射漏了白名单」
   与「补了白名单漏了 `CODE_EXTS`」都真实发生过，靠人记两处必然漏，必须靠断言。
8. 扩展名三张表要对齐：`TEXT_EXT`（进不进管道）、`EXT_TO_GRAMMAR`（有没有语法树）、`CODE_EXTS`
   （算不算代码文件——决定 semantic 类检查跑不跑）。只补前两张会把该语言**当文档审**。

### 5.2 新增一条规则（AST 优先）

1. **先判形态能否静态确认**。能走 AST/token 精筛的，用 `astConfirm: true` + `astConfirmKind` + `kind`
   接到 `lib/ast` 精筛；本引擎不识别的字段（`detection_method`、`require` 一类写法）会被静默忽略，须改用既有字段表达。
2. **在真实语料上量两个数**：正则初筛命中数、精筛后剩余数。
   只报前者就决定收不收，是历史上否决过的方法错误。
3. 精筛后仍有大面积误报的形态规则 ⇒ **不落地**（例：`.Result` 判阻塞、`[0-9]{3,}` 判魔数）。
4. 需要类型/调用图才能判的事实（资源释放、N+1、null 传播）⇒ **不自研**，交给官方分析器，
   只落提示类 notice（例如建议开启 .NET 的 `AnalysisMode=All` / EditorConfig）。
5. 框架专有语义不为特定项目写规则（D6）。
6. 新 kind 若需要豁免，必须同步确认 `exemptHintForFinding({kind})` 真能反查到标记——
   「提示写了但标记不覆盖该 kind」是真实发生过的缺陷（button-bind）。

### 5.3 依赖与资产纪律

- **依赖版本一律精确锁定**（无 caret），并在文档/注释写明为什么不能升（0.27.1 的 ABI 不兼容是实测结论）。
- 新增第三方依赖前先问：能不能被现有能力覆盖？（js-yaml 当初 vendored 就是为了零依赖；
  现在 D1 已改口径，同类需求直接走依赖，不要再抄文件进仓库）。
- 二进制资产不放 `lib/`（放 `assets/`），且必须登记来源、版本、sha256 与可复现下载命令。
- 引入依赖后必须确认 `sync_plugin` 的 deps 校验通过，不能只在本机 dev 环境验证。

### 5.4 门禁与验收（每轮收尾必查）

`scripts/check.mjs`（含层边界：审计层不得依赖 git 层）+ `doc-func/doc-tree/doc-version/doc-drift` 四项
+ 全量回归 `node test/run-tests.mjs --all --concurrency=1`（串行，避免并发跑共享同一仓库的文档用例）。
新增门禁必须**自证会变红**（注入已知坏状态 → 用例转红 → 还原）。

### 5.5 README / 文档

按 `readme-spec`：README 只做使用手册（功能表 + 一行命令 + 参数可空说明 + 环境要求 + API + 文档索引），
机制、依据、踩坑一律进 `docs/` 独立文档，README 不解释、不跳转（文档索引列一行）。

## 六、风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 部署端没装依赖 | js-yaml 缺失 ⇒ 规则加载失败，插件不可用 | `sync_plugin` deps 校验拦在装配期；运行期报明确错误（不静默 0 规则） |
| runtime 与语法 ABI 漂移 | AST 全线失效 | 精确锁版本（D4）+ 每语言 0 ERROR 自检（M2/M3） |
| 大语法使包体膨胀 | 分发变慢 | 实测净增约 1.7MB gzip；wasm 压缩后仅 9% 原体积 |
| 有树后规则命中数变化 | 原本靠「没精筛」侥幸通过的仓库开始报问题 | M2 记录命中数变化；按性价比只调 severity，不为个例特化 |
| 删 vendored 文件误删仍被引用的 | 启动失败 | 删除前先 grep 全部引用点；删除后跑全量回归 |

**回滚**：M1–M4 每阶段独立提交，出问题可单步 `git revert`。
M4 之前 vendored 副本还在仓库里，revert 即回到 vendored 状态；**M4 执行后目录已从工作树删除**，
回滚锚点变成 git 历史（revert M4 那次提交即恢复两个目录），不再有工作树副本。

> 顺序因此定为：**先接通依赖（保留 vendored 副本）→ 验证 → 最后才删包袱（M4）**，
> 不允许一边删一边改。

## 七、未决项

2. **命中数变化后的 severity 基线**：M2 接通 AST 后，若某语言原有规则命中大幅下降/上升，
