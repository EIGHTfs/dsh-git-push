# dsh-git-push v1.60.0 代码不足分析报告

> 分析对象：当前工作区源码（`lib/` / `test/` / `cli.mjs` / `package.json` / `README.md` / `skills/`）
> 方法：全文通读 + `grep` 计数 + `node --check` + 逐文件跑测试。**不引用其他分析文档。**
> 原则：先区分「违反需求的 bug」和「设计选择」；报问题必须给文件 + 行号 + 实测证据。
> 版本：package.json / cli.mjs 均为 `1.60.0`。HEAD：`9d1c9bf`。

## 〇、结论先看

这是一套功能完整、安全闸门较严的 git 管道插件（扫描 → 审计 → commit → api.github.com 推送）。v1.42.0 之后模块拆分清楚，`lib/index.js` 只做调度，规则数据已 YAML 化。

**当前最大短板不在「还能不能跑」，而在「自己宣称的入口已经坏了 / 文档和代码对不上 / 编译产物没被消费」。**

| 维度 | 判断 | 依据 |
|------|------|------|
| 功能正确性 | 中 | 核心单测逐文件全绿，但 `npm test` 入口在 Node 24 直接失败；HTTP/自动推送被内置要求清单永久拦截 |
| 发布完整性 | 低 | `js-yaml` 未声明依赖；`cli.mjs` 不进 npm `files`；无 LICENSE |
| 规则引擎闭环 | 中 | YAML 能编译出 `semanticRules`，审计引擎从不消费 |
| 文档可信度 | 低 | README「注意事项」仍写已废除的同级仓路径；CLI 帮助写了 `--depth` 但解析器不认 |
| 可观测性 | 中 | `runGit` 丢掉 git stderr，失败原因经常是空串 |

## 一、已验证的硬伤（建议修）

### 1. `npm test` 在 Node 24 不可用

`package.json`：

```json
"scripts": { "test": "node --test test/" }
```

实测：

```
Error: Cannot find module '.../dsh-git-push/test'
code: 'MODULE_NOT_FOUND'
ℹ tests 1 / fail 1
```

原因：Node 24 的 `node --test test/` 把目录当模块解析，而不是当测试文件 glob。同目录下 `test/test-*.mjs` 用手写 `ok()` 的那批，本来就不是 `node:test` 套件。

对照：逐个 `node test/test-*.mjs` **14 套件 0 失败**（`test-apply.mjs` 因缺 DSH runtime 主动 skip）。`test-env-inject.mjs` / `test-rules.mjs` 才是真正的 `node:test`。

**影响**：CI / 别人 clone 后第一句 `npm test` 就是红的。作者本机「全绿」靠的是逐文件跑，不是官方脚本。

**改法**：`"test": "node --test test/test-*.mjs"` 不够——手写套件不会被 `node --test` 计断言。要么统一改成 `node:test`，要么 `"test": "for f in test/test-*.mjs; do node \"$f\" || exit 1; done"`。

### 2. 运行时依赖 `js-yaml` 未写入 package.json

三处直接 import：

- `lib/audit.js:23`
- `lib/rule-packs.js:36`
- `lib/readme-gen.js:10`

`package.json` 只有 peer：`@deepseek-ai/dsh-tools` / `dsh-llm` / `schemastery`。**没有 `dependencies`，也没有 `js-yaml`。**

本机 `import('js-yaml')` 能成功，是因为宿主 DSH 的 node_modules 把它提升上来了。纯净 `npm pack` / 独立 CLI（`git-sluice` 自称零第三方依赖）在没有宿主的环境会 `Cannot find module 'js-yaml'`。

讽刺点：自己的 `lib/audit-rules/audit-rules-npm.yml:60-69` 规则 `npm/undeclared-js-yaml` 就是为这件事写的，插件自己踩中。

`package.json` `files` 白名单也漏了 CLI：

```json
"bin": { "git-sluice": "./cli.mjs" },
"files": [ "lib", "skills", "lib/readme-templates", "lib/audit-rules", "docs/code-quality-checklist.yaml", "cordis.patch.yml" ]
```

`cli.mjs` 不在 `files` 里 → npm 发布后 `git-sluice` 命令指向一个不存在的文件。

### 3. HTTP 提交 / 自动推送永远撞上「开发者要求未核对」

`lib/user-requirements.json` 随插件分发，7 条要求。`loadRequirements()`（`lib/workspace-context.js:159-176`）固定读：

1. 配置目录 `requirements.json`
2. **插件内置** `lib/user-requirements.json`（永远存在）
3. 根目录兜底

`found && items.length` 为真时，`commitAndPush` 没有 `requirementsConfirmed:true` 直接拦截（`lib/commit-push.js:24-35`）。

调用链缺口：

| 入口 | 是否传 `requirementsConfirmed` |
|------|-------------------------------|
| 工具 `git_commit_push` | 有参数，AI 可传 |
| CLI `git-sluice commit --req-confirm` | 有 |
| HTTP `POST /api/git-push/commit`（`plugin-http.js:299-301`） | **不传，默认 false** |
| 推送许可自动推送（`plugin-push-permit.js:83-84`） | **不传** |

推送许可默认关闭，所以平时看不出来。一旦用户打开「AI 回复 ✅ 自动推」，会稳定失败：`blocked: true, code: 'USER_REQUIREMENTS'`。HTTP 提交同理。

这不是「门禁设计」，是门禁只接到了 agent 工具，另外两条入口漏接。

但 `ensureRemoteRepo`（`lib/remote-repo.js:70-72`）参数默认是字面量：

工具侧（`plugin-tools.js:162`）：

### 5. CLI 帮助与实现不一致

`cli.mjs` 帮助写了：

```
scan [root] [--depth N]
```

`parseArgv`（32-49 行）只认 `--json / --push / --no-push / --dry-run / --req-confirm / --fail-on-warn / --help / --ruleset / -m`。遇到 `--depth` 走：

```js
else if (a.startsWith('--')) return { pos, flags, bad: a };
```

实测语义：`git-sluice scan /path --depth 5` → `未知参数: --depth`，退出码 1。`cmdScan` 里的 `flags.depth` 永远是 `undefined`，深度恒为 3。

同文件 `printScan`（103-104 行）打印：

```js
未提交=${r.dirty ?? r.uncommitted ?? '-'}
```

`readRepoStatus` 返回的字段是 `changes`（`lib/repo-scan.js:64`）。人读模式下未提交数永远是 `-`。

`cmdFullScan` 还要求目录必须有 `.git`（126 行），但 `fullScanRepo` / `listTextFiles` 本身支持非 git 目录。CLI 把引擎能力砍掉一截。

### 6. `runGit` 丢掉 stderr

`lib/git-core.js:74-82`：

```js
stdio: ['pipe', 'pipe', 'ignore'],
...
stderr: (r.stderr || '').trim()
```

stderr 被 `ignore`，返回值里的 `stderr` 恒为空。`commit-push.js` 失败分支大量读 `add.stderr` / `commit.stderr`（109、140 行），真实 git 报错（身份未知、hook 失败、lock）到调用方是空字符串。排障只能靠 `status !== 0`。

`gitRaw` 同样 `ignore` stderr（108 行）。

### 7. 规则编译了但审计不跑：`semanticRules`

`lib/rule-packs.js:346` 输出桶 `semanticRules: []`，`compileSemanticRule` 把无 pattern、靠 `detection_method` 的规则推进这个桶。`test/test-rule-packs.mjs` 还断言 `semanticRules.length >= 4`。

`lib/audit.js` **零处**读取 `semanticRules`。前端路径穿越、语义类规则编译成功、测试绿灯、提交门禁完全看不见。

同类死代码：

- `lib/ignore-scan.js:4` `import { commitAndPush } from './commit-push.js'`——全文只有注释提到这个名字，运行时不用。它和 `commit-push.js → ignore-scan.js` 构成循环依赖。
- `lib/git-core.js:3` `import { httpsUrlOf, pushViaApi } from './github-api.js'`——本文件不用这两个符号，却和 `github-api.js → git-core.js` 互相 import。
- `lib/core.js:37` `export { readdirSync } from 'node:fs'`——门面把 Node 内置 API 再导出一遍，不是本模块职责。
- `lib/core.js` **不** re-export `gitRaw`（`git-core.js:101` 有导出）。注释还写「re-export 全部原导出」。
- `lib/audit.js:54-57` `applyRulePack`：若传入带 `rules` 数组的包，会丢掉包本身、改去 `getCompiledRulePack(pack.meta?.order)`。热替换接口名存实亡。

### 10. 质量扫描对「本仓库写法」基本失效

`checkSyncInAsync`（`lib/quality.js:184`）只匹配：

```js
/\bfs\.(?:readFileSync|readdirSync|...)\s*\(/
```

本仓库统一是：

```js
import { readFileSync } from 'node:fs';
readFileSync(...)
```

没有 `fs.readFileSync` 前缀 → 自评「性能 10 分」是假阴性，不是真的没有同步 IO。

`checkSilentCatch` 只看 catch 起始行 + 下一行。`catch { /* 注释 */ }` 单行能抓到；多行「只有注释、没有 log」的 catch（本仓大量存在）不报。这是启发式边界，但评分把「健壮性」当真值用，会系统性偏高。

`hasTestFiles` 只看仓库根一层是否有 `test/` 目录名。有目录即满分，不看本次变更有没有对应测试。

## 二、结构性不足（不是立刻崩，但会持续咬人）

### 1. 循环依赖 + 门面过厚

实际环：

```
git-core.js ⇆ github-api.js
ignore-scan.js → commit-push.js → ignore-scan.js
多数 plugin-*.js → core.js 门面 → 再进子模块
```

ESM 循环目前没炸，是因为用到的导出在求值时已经初始化。死 import 一旦有人「顺手用一下」`ignore-scan` 里的 `commitAndPush`，会变成初始化期 TDZ。

`core.js` 37 行 re-export 约 80 个符号，新代码仍从门面进（`plugin-tools.js:11`、`plugin-http.js:15`、`audit.js:24`）。拆分的收益（定位）被「所有人继续 import core」吃掉。

### 2. 规则类型靠字段探测，加规则必须改 if 链

`compileRuleBuckets`（`rule-packs.js:487-499`）顺序：

credref → credfile → secret → func-lines → numeric（内部再拆 6 种）→ regex → semantic

没有显式 `kind`（structure.yml 是唯一写了 kind 的文件）。新规则类型必须插入这条链。这是已定稿、未实施的设计债（见同目录 `DESIGN-2026-09-09-unified-rule-loader.md`，本文不展开那份稿，只确认现状确实是探测链）。

### 3. `fullScan` 名字与「全量审计」撞车

`lib/full-scan.js` 做的是 **AI 对话残留注释扫描**，工具名 `audit_full_scan`。提交门禁默认只扫 `git diff` 新增行。用户要「非 git 目录也能做代码审计 / 提交时扫全量」的 `auditChanged` / `auditFull` **代码里不存在**（全仓 grep 只命中 docs 待办）。

这不是实现 bug，是能力缺口：存量 secret / 超长函数只要本次没改到，门禁就看不见（私密文件扫描是例外，走 `git ls-files`）。

### 4. 查看器复杂度

`getCommitHistory`（`lib/viewer.js:48-83`）：每个 commit 先 `git log --name-only`，再对每个文件 `git diff --numstat`。100 个提交 × 平均 10 个文件 ≈ 1000+ 次 `spawnSync`。只读、无缓存。大仓打开查看器会明显卡。

### 5. `scanRepos` 按目录名去重

`lib/repo-scan.js:106-108`：`seen.has(basename(repoPath))` 则跳过。工作区里两个都叫 `dsh-git-push` 的仓（源码 + 安装副本）只会留下先扫到的那个。这是有意去重 extracted 副本，副作用是「同名真仓」会丢。

### 6. `listTextFiles` 的 gitignore 缓存永不失效

`lib/full-scan.js:158-192`：`gitIgnoreCache` 是模块级 `Map`，按 repoPath 缓存。改 `.gitignore` 后同进程再扫仍用旧集合。插件生命周期很长，附属扫描会漏新忽略 / 误扫已忽略文件。

### 7. HTTP 面无鉴权

`/api/git-push/commit`、`/api/git-push/gen-ssh-key`（响应里带 `privateKey` 路径，`plugin-http.js:161`）、`/api/git-push/permit/config` 均无 token / cookie 校验。这在「DSH 本机设置页、不对外网」前提下是设计；一旦 webServer 绑到非本机，就是未授权提交/改许可/读密钥路径。`readJson` 超 5MB 会 `req.destroy()`，但 `__httpError` 没有调用方检查，超限请求可能被当成缺字段 400，而不是 413。

局域网自用 ≠ 缺陷；缺「仅本机 / 需登录」的显式约束，文档也没写。

### 8. 自动推送绕过 README 核对，且 message 固定

`pushOneRepo`：`showReadme: false`，message 来自配置默认 `chore(ai): 任务完成自动提交`。与 `lib/user-requirements.json` 第一条「禁止空泛词」冲突——就算补上 `requirementsConfirmed:true`，自动提交的 message 仍可能不合格。

## 五、不要当成 bug 的设计（避免误报）

以下是源码注释 / skill / 用户约束里写明的选择，分析时不算缺陷：

1. **禁止直连 github.com**，只走 `api.github.com`，401 才 SSH `ssh.github.com:443`。`githubFetch` hostname 硬闸是需求。
2. **私有仓审计 `blockOn='none'`**（`plugin-audit.js:52-54`）：私有远端只警告不拦截。公开仓保持拦截。
3. **提交前不自动改代码**（v1.45.0）：措辞命中只报、不改写。
4. **CIFS**：`core.filemode=false` + `safe.directory=*`；凭据目录 chmod 失败吞掉（CIFS 改不了 mode）。
5. **同步 fs**：CLI / 审计 / git spawn 本身就是同步管线，不是 web 热路径。问题是质量规则扫不到这种写法，不是「必须全部改 promises」。
6. **`requirementsConfirmed` 对人机工具是故意的**——缺的是 HTTP / 自动推送这两条旁路。
7. **查看器零写操作**：不在页面上 push，推送必须走带审计的工具。

## 六、建议处理顺序（只排序，不执行）
