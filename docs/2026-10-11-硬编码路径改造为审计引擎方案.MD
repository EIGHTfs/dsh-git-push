# 硬编码路径检测：改造为「走审计引擎」+ 版本合并方案

> 落盘时间：2026-10-11 · 状态：**执行中（Round 1 完成 ①-a）** · 目的：防上下文压缩丢失，作为跨轮次交接载体

## 一、目标（用户指令原文要点）

1. **把硬编码路径检测改成调审计引擎** —— 因为审计引擎有自己**动态规则架构**；
2. 规则落位：**新建规则 yml**，把 `nodejs` / `folder` 槽位里与**路径相关**的规则**转**进去；
3. 把「硬编码路径」这几次版本**最终合并成一次新版本**推送。

## 二、背景与根因（为什么必须改）

用户质疑：「审计本身已有硬编码检测，你这个脚本是不是又独立写的检测」——**是的** ✗。实测证据：

| 已有实现 | 位置 | 查什么 |
|---|---|---|
| `security/no-repeated-hardcoded-literals` | `lib/audit-rules/audit-rules-nodejs.yml` | 重复硬编码文本 |
| `security/no-hardcoded-credentials` / `secret-*` | 同上 | 硬编码凭据/密钥 |
| `readability/magic-number-smart` | 同上 | 硬编码魔数 |
| 跨平台可移植性扫描 | `scripts/platform-scan.mjs` | 硬编码 `/tmp`、`C:\Windows`、`sh -c` 等（代码/注释分层） |
| **`scripts/scan-hardcoded-paths.mjs`（我新写的）** | 本轮新增 | 跨系统绝对路径 + fs 可访问性 + 相对路径换算 |

⇒ 第 5 条是**第三份独立实现** ✗ —— 正是本仓库反复在修的「同一事实两份实现 ⇒ 必然分叉」。**结论：删掉脚本自带的 PATTERNS，改为调引擎。**

## 三、已确认的决策（用户已答复）

| 决策点 | 结论 |
|---|---|
| 检测逻辑放哪 | **审计引擎**（正则初筛 + `astConfirmKind` 精筛通道），不写在脚本里 |
| 规则槽位 | **新建 `paths` 槽位**；`nodejs`/`folder` 里路径相关规则**转入**该槽位 |
| 相对路径基准 | **文件所在目录**（`relative(dirname(file), abs)`） |
| 本轮范围 | 先脚本 + 测试；现在扩展为「接入审计 + 版本合并」 |
| 版本处理 | 本轮相关版本**合并成一次新版本**（可 force-push，先建备份引用） |

## 四、引擎接线事实（实测，供后续直接接）

- 槽位是**动态**的：`lib/audit-rules/audit-rules-<槽位名>.yml` 放进去即生效（删掉即失效），**无需改代码**；
- 规则字段：`id / name / category / severity / description / patterns|pattern / astConfirm / astConfirmKind / exceptions / fixable / mitigation`；
- **精筛通道**：`lib/checks/regex.js` 按 `rule.astConfirmKind` 分派到 `lib/checks/common.js`（如
  `shellCdDynamicLines`、`writeIntoGitignoreLines`）与 `lib/ast/shell.js`；精筛可拿到**文件路径与仓库上下文**
  （`repoPath`）——正则拿不到，这正是"可访问性判断 + 相对路径换算"该待的地方；
- 审计入口：`scripts/audit-runner.mjs`（`runAuditExt`，`lib/audit/ext-runner.js`）；核心审计 `auditFull/auditWithScope` 会自动并入 ext findings；
- 计数口径（`scripts/doc-drift.mjs` 会盯）：槽位 = `lib/audit-rules/*.yml` 文件数；规则 = `^  - id:` 行数。
