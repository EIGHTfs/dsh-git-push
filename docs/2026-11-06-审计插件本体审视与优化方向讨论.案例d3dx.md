# 审计插件本体审视与优化方向讨论 —— 案例：外部 Python 仓库全量审计

> 状态：**方向讨论记录，未动代码**。确立日期 2026-11-06。
> 案例事实：对一个外部 PySide6 仓库（1300 文件 / 38.4 万行 / 2150 提交）做全量审计，
> 结果 85.296/A（77 blocker / 4832 warning），随后逐条人工核实。
> 本文档目的：借这次案例，审视「多层审计架构 + 误报补丁」模式本身的维护性，并给出优化方向候选。

---

## 一、案例结果对照：分数说「A」，人工核实说「两回事」

### 1.1 静态审计给出的结论
- 评分 85.296 / A；安全性、性能、测试覆盖、可观测性、开发者体验 5 个维度**满分 10**。
- 77 条 blocker，其中 10 条 `security/no-hardcoded-credentials`。

### 1.2 人工逐条核实后的结论
| 静态审计输出 | 核实结果 |
|---|---|
| 10 条凭据 blocker | **全部误报**：`token = "plugin-preset:" + uuid4().hex`、`def _icon(name, token="text.secondary")`、`fill_token = "accent.subtle"`——全是 CSS 主题令牌名 / 运行时 uuid 前缀 |
| 5 个维度满分 | **测不到而满分**：全仓规则绑定密度（yml `dimensions` + 编译器默认绑定）实测——测试覆盖 0 处、可观测性 0 处、开发者体验 0 处、安全性仅 3 处、性能仅 2 处 |
| 4832 warning | **86% 是风格噪音**：magic-number 2930 + 复杂度 656 + 函数长度 299 + 变量名 286 = 4171 |
| 真问题（人工实测发现 6 条） | **插件一条 blocker 都没报**（见 1.3） |

### 1.3 人工发现、插件漏掉的 6 条（均实测复现）
1. **压缩包路径穿越**（高危，实测逃逸成功）：`extract_files()` 的 RAR 分支 `dest / name` 裸拼接写盘，成员名 `../PWNED.png` 落到目标目录之外；同仓库其他三条路径（zip 整包 / rar 整包 / 插件安装器）都有穿越防护，唯独这条调用链三处调用方全部裸奔。
2. **插件扫描器可绕过**（高危，实测 ok=True）：AST 黑名单（`eval/exec/compile/__import__` + 危险模块表）拦不住 `importlib.import_module("o"+"s")` + `getattr(_os,"sy"+"stem")` 拼接。
3. **516 个测试文件但 CI 一个都不跑**（中危）：`.github/workflows/` 只有 release.yml。
4. **HMAC 密钥公开硬编码**（中危）：`APP_UPDATE_TOKEN_SECRET = b"d3dx..."`——插件凭据规则**恰好漏报**，因为它是 Python **bytes 字面量**，tokenizer 只认 `str` token（见 2.1）。
5. **自更新 SHA256 可选校验 + 摘要与产物同源**（中危）：`if info.sha256 and ...` 短路放行；镜像通道同时提供 zip 与正文摘要，校验自证。
6. **133 处 `except Exception:` 紧跟 `pass`**（低-中）：插件没有 catch-pass 类规则（有 `quality/empty-catch` 但只覆盖 JS 槽位）。

**定性**：当前引擎是可靠的「代码规范合规扫描器」，不可靠的是「缺陷/漏洞发现器」。而评分模型把前者的高产出误呈现为后者的健康度。

## 二、维护性根因：多层架构的结构性代价（本体数据）

### 2.1 误报-补丁循环的量化痕迹
| 指标 | 实测值 | 含义 |
|---|---|---|
| 审计代码总量 | **14327 行**（ast 6056 / audit-rules 3229 / audit 3225 / checks 2903 / rule 1233 / exempt 544 / score 366） | 自研规模远超规则本身 |
| 规则 / 正则 / AST 精筛 | 169 条规则，244 处 pattern，62 处 astConfirmKind | 每条误报都可能横跨「正则粗筛→AST 精筛→回退 token 级」三层 |
| 「修误报」提交 | **40 / 438（9%）** | git log 含误报/漏报/误伤/false positive 的提交 |
| 注释里的补丁痕迹 | **121 处**「误报/漏报/撤回/刻意不/防后门/特例」 | credential.js 9 处、tokenizer.js 10 处、magic-number.js 7 处——判定函数里大半体积在写「不报什么」 |
| 凭据规则双向失灵 | 误报：`isMeaningfulCredentialValue("text.secondary")=true`；漏报：bytes 真密钥整行不被识别 | 同一弱判据（变量名撞词 + 值非占位符）的两面：**既拦不住不像凭据的枚举名，也拦不住不像 str 的凭据** |

### 2.2 结构性诊断（为什么「越来越难以维护」是必然）
- **判定语汇自研且单向生长**：每条误报修复都在加特例（剥前缀再判、跨语句边界 break、文档行内代码段兜底……），特例之间互相引用（「两处检查共用一套判据否则漂移」的注释本身就说明漂移发生过）。规则数线性增，判定函数的组合状态指数增。
- **正则粗筛层是误报的发动机**：244 处 pattern 先制造候选，再由 62 处 astConfirm 收窄——收窄不了的（如凭据 kind 的「右侧是任意非空字符串」）就漏到用户面前。10-28 方案 D3 已认定「按正则命中数收规则属方法错误」，但存量规则里仍有大量「正则形状即报」的条目。
- **无外部知识源**：全仓 0 处接入 ruff/eslint/golangci/clang-tidy 的结果。而这些项目自带的工具链（案例仓库 pyproject 里就写着 `ruff==0.17.2` + line-length=120）对风格类问题的判定精度、语言演进跟进，**必然**优于自研正则——我们却在为 ruff 一条规则（S105 hardcoded string）的等价物维护 199 行特例代码。
- **评分诚实度缺陷放大认知成本**：`dims[d]=10-k·ln(1+count)` 在 count=0 时恒为满分，动态权重口径「无命中维度不缩放」让零规则维度（测试覆盖/可观测性/开发者体验）以满权重拉高总分。**分数越好看，越没人追问「这个维度真的被测了吗」**——误报修补的动力也被虚高分消解。

## 三、优化方向候选（未拍板，按杠杆排序）

### 方向 A：外部 linter 委托层（治本，杠杆最大）
> 与 D1（弃零依赖）同一逻辑的延伸：既然 wasm 可以走 npm，诊断结果为什么不能走官方工具链？

- 新增「适配器槽位」：检测仓库既有配置（`pyproject.toml[tool.ruff]` / `eslint.config.*` / `.editorconfig` / `go vet`），有则调用其 JSON 输出、映射进统一 finding 结构（severity/dimensions/豁免注释兼容 noqa/ESLint-disable）；无则跳过（同 D5：绝不硬失败）。
- **自研引擎让位**：风格类（magic-number、函数长度、复杂度、命名、行长）逐步从「判定者」退为「无外部工具时的回退」。121 处特例中最难维护的判定语汇直接失去增量来源——新项目都有 ruff/eslint，覆盖只会上升。
- 收益模型：误报源头（正则粗筛）移出主干；风格维度精度=官方工具精度；维护成本从「逐语言逐规则」降为「逐工具一个适配器」。
- 成本：适配器本身（每种输出格式一个）+ 依赖存在性探测 + 版本输出差异容错。属新架构层，需要 10-28 式的决策清单。

### 方向 B：评分诚实度修正（小改动，高必要）
1. **零规则维度不记满分**：维度实际绑定规则数=0 ⇒ 不计入分母，报告标注「本维度无检测能力」（防「满分≠测过」再误导）。
2. **覆盖率进摘要**：规则数/语言文件数/外部工具可用性作为审计元数据输出——读者先看到「测了什么」，再看分数。
3. （可选）**规则双向样本自检**：每条高危规则（凭据/注入/穿越）维护一组「必报正样本 + 必不报负样本」进测试；误报修复与漏报检查同一次提交完成，杜绝修 A 漏 B（案例里凭据规则只测了「字符串字面量」正样本，bytes 负形漏报无人知晓）。

### 方向 C：存量高危规则精筛补强（战术，按 D3 门槛）
- 凭据 kind：补 bytes/raw/f-string 字面量前缀识别（堵案例漏报 #4 同类）；值判据从「非占位符」升级为「形状像凭据（ghp_/sk-/AKIA/40+ 位 base64/高熵）才 blocker，枚举名样式降 notice」。
- 新增 catch-pass 语言无关检测（案例 #6；JS 槽位已有 empty-catch，py/go 无）。
- **谨慎扩充**：每加一条判定都在 2.1 的指数里加一项——新增判定优先走方向 A（委托），A 覆盖不了的才自研（如案例 #1 的跨函数数据流，D3 已定「需数据流信息不自研」，如实归入「人工核查提示」并在报告里显眼列出，而不是藏在 4832 行噪音里）。

### 方向 D：报告降噪（体验，低成本）
- blocker 摘要按「规则族」聚合而非逐行；风格类默认折叠；「人工核查提示」类（scoreImpact=0）单列成节——案例里真正该看的东西全被埋。

**推荐组合**：B（先让分数可信）→ A（建委托层，停止给自研风格规则添丁）→ C（存量高危只补最小面）→ D。

## 四、留给下一轮的问题
1. 方向 A 的委托边界：外部 linter 的 finding 进不进拦截门禁（blocker），还是只进评分与报告？（涉及「别人的规则集裁决我的提交」的权责）
2. 零规则维度剔除后，历史分数口径断裂（同一仓库改前改后不可比），要不要版本化评分（score schema v2）？
3. 案例 #1 类「同仓库多实现不同步」问题（正确防护存在三处、漏一条链），是否值得做「防护函数调用覆盖率」类元规则？它恰好是自研数据流的反例——建议不做（D3/D6 口径），用「安全敏感函数清单 + 人工核查提示单列」替代。
