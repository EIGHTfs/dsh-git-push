## 一、四条对照纪律（执行检查单）

### 3.1 槽位发现与顺序（2026-09-11 已测，双向对照）

**v1（旧项目 lib/rule-packs.js）实测：**
- RULE_SLOTS = comment,dsh,frontend,nodejs,npm,private,structure,template,version（9 个，private/template 特殊）
- DEFAULT_RULE_ORDER = comment → dsh → frontend → nodejs → npm → structure → version（7 个，剔除 template/private）
- meta.count = 9（各 yml metadata.name/description 齐全；comment=「注释质量检测规则（AI 交流注释识别）」）

**v2（lib/rule/loader.js）实测：**
- discovered = comment,docs,dsh,folder,frontend,i18n,nodejs,npm,performance,private,robustness,structure,template,version（14 个）
- 配置顺序优先：resolveSlotOrder(['comment','nodejs']) → comment → nodejs → 其余偏好序 → private 恒末尾，template 不加载
- meta 读取正常（comment=「注释质量检测规则（AI 交流注释识别）」一致）

**对照结论：** 行为一致（配置优先/后覆盖前/private 恒末尾/template 默认不加载）；槽位数 v2 14 > v1 9，
多出的 docs/folder/i18n/performance/robustness 为「3 种新 yml + 扩展」落实（用户 2026-09-11 确认，非漂移）。

### 3.2 审计门禁（commitWithAudit / v1 CLI audit 语义）
- 输入：同一个 v2 仓库全量审计
- v1（旧项目 CLI `git-sluice audit <repo>`）：退出码 0 放行（质量评分 77 B 级，拦截=true 表示有 warning 级别提示但不拦截）；blocker 命中时退出码 2
- v2（auditWithScope）：`{ ok:true, scope, repo, findings, summary, files }`；commitWithAudit 在 `summary.blocker > 0` 时返回 `{ ok:false, blocked:true, error:'审计拦截：N 个 blocker' }`
- 对照结论：拦截语义一致（error→blocker 拦截 / warning→提醒 / info→pass）；v2 用返回值而非退出码表达（引擎可脱离 CLI 用）
