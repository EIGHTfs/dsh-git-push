# 多语言 AST 接通实测记录（M2）

> 用途：记录 M2「多语言 AST 接通」的改前/改后命中数，作为 M3 按 D3（以精筛后剩余误报为准）取舍规则的量化依据。
> 口径：正则初筛命中数 ≠ 真实缺陷数；每一行都标清是「正则初筛 / token 级精筛 / 语法树精筛」哪一档。
> 复现方式：`DSH_GIT_PUSH_TS_ASSETS=<不存在的目录>` 为「无语法树」臂，默认配置为「有语法树」臂。

## 一、改了什么

| 位置 | 改动 |
| --- | --- |
| `lib/ast/treesitter.js` `EXT_TO_GRAMMAR` | 新增 `cs→c_sharp`、`c→c`、`cpp/cc/cxx/hpp/hh/hxx→cpp`、`h→cpp`、`go`、`java`、`kt→kotlin`、`php/phtml→php`、`rs→rust`、`swift` |
| `lib/audit/collector.js` `TEXT_EXT` | 新增 `cs`、`cc`、`cxx`、`hh`、`hxx`、`mts`、`cts`；并导出该常量供门禁断言读取 |
| `lib/audit/finding.js` `CODE_EXTS` | 新增 `c`、`cc`、`cxx`、`cpp`、`h`、`hpp`、`hh`、`hxx`、`cs`、`phtml` |
| `test/test-treesitter-grammars.mjs` | 新增多语言自检 + **永久门禁**：`EXT_TO_GRAMMAR` 的每个键都必须在 `TEXT_EXT` 里 |

三处白名单的分工（缺任何一处都会「看着接通、其实没生效」）：

- `EXT_TO_GRAMMAR`：决定这个扩展名**用哪个语法树**；
- `TEXT_EXT`：决定这个文件**进不进审计管道**（不进管道 ⇒ 规则永远 0 命中）；
- `CODE_EXTS`：决定这个文件**算不算代码**（不算代码 ⇒ `semantic` 类检查整体跳过，`audit-file` 按非代码处理）。

`.h` 归 `cpp` 而不归 `c`：两者共用该扩展名，cpp 语法是 C 的超集。交给 `c` 语法时，合法 C++ 头文件会解析出 ERROR ⇒ 整棵树作废、退回 token 级（等于白接）；反之把纯 C 头交给 cpp 语法不会报错。

### 4.2 多语言样本语料上（三档计数）

| 规则 | 正则初筛 | token 级（无树） | 语法树（有树） |
| --- | --- | --- | --- |
| `cpp/raw-new` | 4 | 2 | 2 |
| `php/error-suppression` | 2 | 1 | 1 |
| `rust/unimplemented-macro` | 2 | 1 | 1 |
| `rust/panic-macro` | 3 | 2 | 2 |
| `rust/println-debug` | 2 | 1 | 1 |
| `rust/unsafe-block` | 2 | 1 | 1 |
| `performance/busy-wait-loop` | — | **2** | **0** |

六槽位汇总（无树 → 有树，blocker/warning）：cpp 1/5→1/5、go 1/4→1/4、java 0/2→0/2、php 2/2→2/2、rust 2/3→2/3、swift 2/4→2/4。

### 4.3 结论：树只被 `astConfirmSpan` 规则消费

`cpp/raw-new`、`php/error-suppression`、`rust/*` 写的是 `astConfirm: true`，引擎对它们的精筛走 **token 级行列判定**（`lib/checks/regex.js` 的 `makeCodeSpanFilter`），**不查语法树**；语法树只在规则声明 `astConfirmSpan: true` 时才参与（`performance/memory-bomb`、`performance/busy-wait-loop`）。因此：

- 六槽位「有树前后命中数不变」是引擎现状的必然结果，不是接通失败；
- 语法树确实在跑的判别证据是 `performance/busy-wait-loop`：`2 → 0`——两处命中是**带内层引号的原始/逐字字符串**，token 级在内层引号处提前收尾、把剩余部分当代码而误报，语法树正确整段判为字符串；
- 要让 `astConfirm` 也吃树，属于改判定逻辑，不在 M2 范围。

## 六、永久门禁：映射与白名单必须同步

`test/test-treesitter-grammars.mjs` 断言「`EXT_TO_GRAMMAR` 的每个键都在 `TEXT_EXT` 里」，并自证会变红（临时从 `TEXT_EXT` 删 `cs`）：

```
# 删掉 cs 后
not ok 2 - 门禁：EXT_TO_GRAMMAR 的每个扩展名都必须在 TEXT_EXT 收集白名单里
    这些扩展名映射了语法却没进收集白名单（文件不会进管道）：cs
# tests 5
# pass 4

# 还原后
ok 2 - 门禁：EXT_TO_GRAMMAR 的每个扩展名都必须在 TEXT_EXT 收集白名单里
# tests 5
# pass 5
```

反向不设断言：`TEXT_EXT` 有、`EXT_TO_GRAMMAR` 没有是合法的（那些扩展名走 token 级回退）。

## 七、对 M3 的输入

1. **高信号、值得先做**：`quality/empty-catch`（C# 33 条 / 13 文件，抽查全为真 `catch { }`）；`throw ex`、弱加密 API、SQL 拼接属同档（形态可静态确认）。
2. **量大、需先抽样定 severity**：`max-cyclomatic-complexity` 322 条 / 138 文件、`vague-variable-name` 52 条 / 36 文件——集中在少量 Unity 手写代码文件，先抽 10 个文件核真伪，否则 446 条 warning 全是门禁噪音。
3. **规则需先修再收**：`no-repeated-hardcoded-literals` 在 C# 上 41 条里 10 条是插值串误报（24%），修完提取口径才适合进 M3。
4. **必须先核来源**：`secret-email` 5 条（error 级）要确认是真实凭据还是资源文件里的邮箱。
5. **不建议落地**（与 D3 / 5.2 一致）：`.Result` 判阻塞（无类型信息必误报）、`[0-9]{3,}` 判魔数（本语料正则口径 7022 处）、Unity 框架专有语义（D6）。

## 八、遗留

1. **可选下一步：接剩余语法**。`tree-sitter-wasms` 里还有 dart / lua / ruby / scala / zig / elixir / elm / objc / ocaml / solidity / ql / rescript / systemrdl / tlaplus / embedded_template / bash / html / css / json / toml / yaml / vue / tsx 等语法，但本仓库**没有对应语言规则包**。按既定口径「加载哪些语言 = 存在哪些语言规则包」，映射它们只会让文件进管道却没有专属规则（仅受语言无关规则覆盖），故本轮不接。
2. C# 没有 `audit-rules-csharp.yml`（按里程碑属 M3），槽位统计里也没有 csharp 槽位。
3. 真实 C# 语料里没有 cpp/go/java/php/rust/swift 文件，六槽位的「有树前后」变化只在 7 个文件的样本语料上量到，样本量小，不能代替真实语料。
4. `secret-email` 5 条未逐条抽查（本轮时间用在 CODE_EXTS 增量上），M3 需补。

### 9.3 落点与门禁

- 新槽位 `lib/audit-rules/audit-rules-csharp.yml`：`exts: ["cs"]`，3 条规则，全部 `astConfirm: true` + `astConfirmSpan: true`。
  只写 `astConfirm` 时按「行」判：`const string S = "throw ex;";` 这种行仍是代码行，字符串里的同名文本会被报出来；加 `astConfirmSpan` 后按命中列判（有 c_sharp 树时用树，无树时回退 token 列级），才是真排除。
- 测试 `test/test-audit-rules-csharp.mjs`：槽位发现 / 该报 / 不该报 / 注释与字符串不算代码 / `exts` 不污染其它语言，共 5 个用例。
- 文档计数：`docs/SPEC.md`、`docs/功能-审计规则体系.md` 的「22 个槽位 / 165 条规则」更新为「23 / 168」（新增槽位 1、新增规则 3；数字取自 `doc-drift` 的实测口径）。
