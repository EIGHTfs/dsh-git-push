## 二、误报分两类

### ① 自家约定规则外溢（最严重）

| 规则 | 命中 | 问题 |
|------|------|------|
| `version/format-not-triple` | **1441**（DestinyChildLive2D 1435 + Azure-Gravure 6） | 规则本意是「自家插件版本号必须 X.Y.Z」，却扫所有 `.json`/`.md`：第三方资源仓库里成千上万个 json 带 `"version": "1.0"` 之类字段 → 逐条报 **blocker** |
| `version/changelog-many-entries` | 89（SpineViewer 85 + ShinySpineViewer 4） | 本意是「一次提交 = 一个小版本」的自家提交纪律；第三方 CHANGELOG 天然多版本 → 逐行报 |

根因：version 槽位规则没有「只对自家仓库生效」的闸门（`dsh` 槽位靠"命中率低"约定，version 槽位在第三方仓库命中率极高）。

### ② 风格/质量规则刷屏（第三方 + 构建产物）

`readability/magic-number-smart`（约 140）、`readability/variable-min-length`（约 130）、
`readability/vague-variable-name`（约 145）、`security/no-repeated-hardcoded-literals`（约 53）、
`robustness/io-risk` / `timeout-on-external-api`（各约 30）。

特征：**同一文件同一规则动辄几十上百条**（spive2d 96 个文件报 554 条），且大量落在
**打包产物 / 压缩后的 js**（live2d-viewer-web、blue-archive-viewer 带 `.map` 数千个）上。

## 三、优化候选（待讨论，本文不实施）

1. **version 槽位加自家仓库闸门**：仅当 `package.json` 的 `name` 以 `dsh-` 开头（或 gbmd 三组件）时加载该槽位 —— 与 `appendSplitDocsCheck` 已有的「只对 dsh 插件仓库生效」同款做法。
2. **同文件同规则去重**：同一文件同一规则最多报 1 条（附命中数），把 1435/117/85 这类刷屏压成一条。
3. **产物目录/文件降权或跳过**：`*.min.js`、`*.map`、`dist/`、`build/` 等打包产物默认不跑风格类规则。
4. **纯资源仓库快速跳过**：文本文件极少、且以图片/模型为主时，只跑结构类检查，不跑语言风格规则。
5. **兜底提示**：命中被截断（`audit/scan-truncated`）时明确告知「本次只扫了前 N 个文件」，避免用户以为全扫过了。

## 四、边界

- 语料是第三方项目，**不是**按本插件规范写的，命中不等于代码有问题——这正是误报分析的价值。
- 各项目体积大（合计约 26 GB），本次为**全量扫描 + 文件上限截断**，未做逐行人工复核。
- 优化落地时必须同时验证自家仓库（dsh-git-push / ai-work-archive）的审计结果不被放松。
